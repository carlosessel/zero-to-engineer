By the end of this chapter you will write tests that catch real bugs and still let you change the code freely: you will know what to test at each level, how to write clear unit tests, when to use fakes, stubs and mocks (and when not to), how test-driven development works, how to test against a real database, and how contract, property-based and mutation testing find bugs that ordinary tests miss. The web course introduced Vitest; this chapter is about testing well, in any language.

## Why test

Tests are code that checks other code behaves as intended. Their main value is not finding today's bugs but making **change safe**: a good test suite lets you refactor, upgrade a library or add a feature and know within minutes whether you broke something (<Ref to="m-refactoring" />). Tests are also **executable documentation**: a well-named test says exactly what the code promises.

A test suite is worth having only if people trust it. Trust needs tests that are:

- **Fast**, so they are run constantly (a unit test in milliseconds, the whole suite in minutes).
- **Isolated**: each test sets up what it needs and does not depend on other tests or their order.
- **Repeatable**: the same result every run, on every machine. No dependence on the real clock, the network, randomness or leftover data.
- **Self-checking**: pass or fail with no human reading output.
- **Focused on behaviour**: they fail when the behaviour is wrong, and not when the code is merely restructured.

(The first letters of the first four, plus "timely", give the acronym **FIRST**.)

## The test pyramid

Tests come at different levels:

- **Unit tests** check a small piece (a function, a class, a domain object) on its own. Fast, precise, and cheap to write.
- **Integration tests** check that several pieces work together, including real infrastructure: your repository against a real database, your HTTP handler with its middleware, your code calling a message broker.
- **End-to-end tests** (E2E) drive the whole system as a user would, through a browser or the public API. They are the most realistic, and the slowest, most brittle and hardest to debug.

The **test pyramid** (Mike Cohn) recommends many unit tests, fewer integration tests and a small number of end-to-end tests, because the cost and flakiness rise towards the top. Some teams prefer a **testing trophy** (Kent C. Dodds) with integration tests as the widest band, because those catch the bugs that matter most in applications that are mostly glue. Both agree on the essentials: most tests should be fast, and end-to-end tests should cover only the critical journeys (sign up, check out, pay).

## Writing a good unit test

A unit test usually has three parts, often called **arrange, act, assert** (or given, when, then):

```ts
export type Line = { pence: number; qty: number };

export function basketTotal(lines: Line[], memberDiscountPercent = 0): number {
  const subtotal = lines.reduce((sum, l) => sum + l.pence * l.qty, 0);
  const discount = Math.round((subtotal * memberDiscountPercent) / 100);
  const delivery = subtotal - discount >= 3000 || subtotal === 0 ? 0 : 350;
  return subtotal - discount + delivery;
}
```

```ts
import { describe, expect, it } from "vitest";
import { basketTotal } from "./basket";

describe("basketTotal", () => {
  it("adds £3.50 delivery to small baskets", () => {
    const lines = [{ pence: 450, qty: 2 }];

    const total = basketTotal(lines);

    expect(total).toBe(1250);
  });

  it("delivers free from £30 after discount", () => {
    expect(basketTotal([{ pence: 1500, qty: 2 }])).toBe(3000);
  });

  it("charges delivery when a discount takes the basket under £30", () => {
    expect(basketTotal([{ pence: 1500, qty: 2 }], 10)).toBe(3050);
  });

  it("charges nothing for an empty basket", () => {
    expect(basketTotal([])).toBe(0);
  });
});
```

All four tests pass. Notice what makes them good:

- **Names state the behaviour** in the language of the business ("charges delivery when a discount takes the basket under £30"), so a failure explains itself.
- **One behaviour per test**, with only the data that matters to it.
- **Boundaries and edge cases**: exactly £30, a discount pushing it under, an empty basket. Most bugs live at boundaries (off-by-one, empty, zero, the maximum).
- **No logic in tests**: no loops or conditions that could themselves be wrong. Expected values are literal numbers worked out by hand.
- **Testing the public behaviour**, not private helpers or internal calls, so the function can be refactored freely.

Java uses JUnit and C# uses xUnit or NUnit in the same shape:

```java
import static org.junit.jupiter.api.Assertions.assertEquals;

import java.util.List;
import org.junit.jupiter.api.Test;

class BasketTest {
    @Test
    void chargesDeliveryWhenADiscountTakesTheBasketUnderThirtyPounds() {
        var lines = List.of(new Line(1500, 2));

        long total = Basket.total(lines, 10);

        assertEquals(3050, total);
    }
}
```

## Test doubles

A unit often depends on things that are slow, unpredictable or have side effects: a database, an email service, a payment provider, the clock. A **test double** (Gerard Meszaros's term) stands in for the real thing in a test. There are five kinds:

- A **dummy** is passed but never used (to fill a parameter).
- A **stub** returns canned answers ("the price service says 450").
- A **spy** records how it was called, so the test can check afterwards.
- A **mock** is set up with expectations of how it should be called and fails the test if they are not met.
- A **fake** is a working, simplified implementation, such as an in-memory repository (<Ref to="m-enterprise-patterns" />).

```ts
export interface Mailer {
  send(to: string, subject: string): Promise<void>;
}

export interface Clock {
  now(): Date;
}

export async function remindUnpaid(
  invoices: { email: string; dueOn: string; paid: boolean }[],
  mailer: Mailer,
  clock: Clock,
): Promise<number> {
  const today = clock.now().toISOString().slice(0, 10);
  const overdue = invoices.filter((i) => !i.paid && i.dueOn < today);
  for (const invoice of overdue) await mailer.send(invoice.email, "Your invoice is overdue");
  return overdue.length;
}
```

```ts
import { expect, it, vi } from "vitest";
import { remindUnpaid } from "./reminders";

it("emails only unpaid invoices that are past due", async () => {
  const mailer = { send: vi.fn().mockResolvedValue(undefined) };
  const clock = { now: () => new Date("2026-11-13T09:00:00Z") };
  const invoices = [
    { email: "ama@example.com", dueOn: "2026-11-01", paid: false },
    { email: "kofi@example.com", dueOn: "2026-11-01", paid: true },
    { email: "esi@example.com", dueOn: "2026-11-20", paid: false },
  ];

  const sent = await remindUnpaid(invoices, mailer, clock);

  expect(sent).toBe(1);
  expect(mailer.send).toHaveBeenCalledTimes(1);
  expect(mailer.send).toHaveBeenCalledWith("ama@example.com", "Your invoice is overdue");
});
```

The test passes. The clock is a **stub** (a fixed date, so the test gives the same result every day) and the mailer is a **spy** made with `vi.fn()` (Mockito and Moq do the same in Java and C#). Both were easy to pass in because the function receives its dependencies (<Ref to="m-solid" />).

### Don't over-mock

Mocks are powerful and easy to overuse. A test that mocks everything and checks every internal call ("then it called `repository.findById` with 7, then `mapper.toDto`…") tests the *implementation*, not the behaviour: it breaks on every refactoring and passes even when the real pieces do not fit together. Guidelines:

- **Mock at boundaries you own**: your `Mailer` interface, not the third-party SMTP library.
- **Prefer fakes and real objects** for things inside your system; use real domain objects, never mocks of them.
- **Check outcomes** (what was returned, what state changed, which message was sent) rather than the sequence of internal calls.
- If a test needs many mocks, the code under test probably has too many dependencies.

## Test-driven development

**Test-driven development** (TDD), popularised by Kent Beck, writes the test *before* the code, in a short cycle:

1. **Red**: write a small failing test for the next bit of behaviour. Watch it fail, which proves it can fail.
2. **Green**: write the simplest code that makes it pass.
3. **Refactor**: clean up the code and tests while everything stays green.

Repeat every few minutes. TDD's benefits are mostly about design: writing the test first forces you to decide the interface from the caller's point of view, keeps units small and dependencies injectable, and leaves every line covered by a test that once failed. It works best for logic with clear inputs and outputs. It is harder, and less valuable, for exploratory work or user-interface layout; many good engineers use it selectively, for example always writing a failing test before fixing a bug (<Ref to="m-debugging" />).

## Integration tests with real infrastructure

Unit tests with fakes cannot tell you whether your SQL is valid, your migration works, your ORM mapping is right or your query uses the index. For that, test against the **real thing**. In-memory substitutes (H2 instead of PostgreSQL, SQLite instead of SQL Server, EF Core's in-memory provider) behave differently in many small ways and give false confidence.

**Testcontainers** (for Java, .NET, Node.js, Go, Python and more) starts real services in Docker containers from inside a test, and throws them away afterwards:

```ts
import { PostgreSqlContainer } from "@testcontainers/postgresql";
import { Client } from "pg";
import { afterAll, beforeAll, expect, it } from "vitest";

let container: Awaited<ReturnType<PostgreSqlContainer["start"]>>;
let db: Client;

beforeAll(async () => {
  container = await new PostgreSqlContainer("postgres:17").start();
  db = new Client({ connectionString: container.getConnectionUri() });
  await db.connect();
  await db.query("create table orders (id serial primary key, customer text not null, pence int not null check (pence > 0))");
}, 120_000);

afterAll(async () => {
  await db.end();
  await container.stop();
});

it("rejects an order with a non-positive total", async () => {
  await expect(db.query("insert into orders (customer, pence) values ('c-17', 0)")).rejects.toThrow(/check constraint/);
});
```

Each test run gets a fresh, real PostgreSQL, so the check constraint, the SQL and the driver are all tested for real. Keep integration tests fast by starting containers once per test file (or per run), and reset data between tests with transactions that roll back or by truncating tables.

## Contract testing

When services call each other (<Ref to="m-architecture" />), each side's unit tests can pass while the two disagree about the API: the provider renamed a field the consumer reads. End-to-end tests of every pair of services are slow and fragile. **Consumer-driven contract testing** (with tools such as **Pact**) solves this: the consumer's tests record the requests it makes and the responses it relies on as a **contract**; the provider's build replays those requests against the real provider and checks that its responses still satisfy every consumer's contract. A breaking change fails the provider's build before deployment. OpenAPI-based schema checks (<Ref to="m-api-design" />) are a lighter alternative.

## Property-based testing

Example-based tests check the cases you thought of. **Property-based testing** checks a property that should hold for *all* inputs, by generating hundreds of random inputs, and when it finds a failure it **shrinks** it to the smallest input that still fails. Libraries include fast-check (TypeScript), jqwik (Java), FsCheck and CsCheck (.NET) and Hypothesis (Python).

The idea fits in a few lines. Suppose a function splits a bill between people in whole pence:

```ts
function splitBill(totalPence: number, people: number): number[] {
  const share = Math.round(totalPence / people);
  return Array.from({ length: people }, () => share);
}

let seed = 7;
const random = (max: number) => {
  seed = (seed * 1103515245 + 12345) % 2 ** 31;
  return seed % max;
};

for (let run = 0; run < 1000; run++) {
  const total = random(100_000);
  const people = 1 + random(12);
  const sum = splitBill(total, people).reduce((a, b) => a + b, 0);
  if (sum !== total) {
    console.log(`property failed: split(${total}, ${people}) adds up to ${sum}`);
    break;
  }
}
```

It prints `property failed: split(82176, 9) adds up to 82179`: a randomly generated case quickly breaks the property "the shares add up to the total", which an example like `split(900, 3)` never would. A real library would also shrink it to something tiny like `split(1, 2)`, where rounding gives each person 1p and the shares add up to 2. The fix gives the leftover pence to the first few people:

```ts
function splitBill(totalPence: number, people: number): number[] {
  const base = Math.floor(totalPence / people);
  const remainder = totalPence - base * people;
  return Array.from({ length: people }, (_, i) => base + (i < remainder ? 1 : 0));
}

console.log(splitBill(82176, 9), splitBill(1, 2));
```

It prints `[9131, 9131, 9131, 9131, 9131, 9131, 9130, 9130, 9130] [1, 0]`: the shares add up to 82,176 exactly. Good properties to test: **round trips** (`decode(encode(x))` equals `x`), **invariants** (totals add up, a sorted list stays the same length), **comparison with a simple reference implementation**, and "never throws on any input".

## Coverage and mutation testing

**Code coverage** measures which lines or branches the tests executed. Low coverage reliably shows untested code; high coverage does not show the tests are good: a test that calls a function and asserts nothing gives 100% coverage. Use coverage to find gaps, not as a target to hit.

**Mutation testing** measures test quality directly. A tool makes many small changes to your code (**mutants**: `>=` becomes `>`, `+` becomes `-`, a condition becomes `true`) and runs the tests against each. If a test fails, the mutant is **killed**; if all tests still pass, the mutant **survived**, meaning no test notices that change. Tools include Stryker (JavaScript, TypeScript, C#) and PIT (Java).

```ts
const original = (subtotal: number) => (subtotal >= 3000 ? 0 : 350);
const mutant = (subtotal: number) => (subtotal > 3000 ? 0 : 350);

const weakTests = [[1000, 350], [5000, 0]];
const boundaryTests = [...weakTests, [3000, 0]];

const killedBy = (tests: number[][]) => tests.some(([input, expected]) => mutant(input) !== expected);
const passOriginal = (tests: number[][]) => tests.every(([input, expected]) => original(input) === expected);

console.log(passOriginal(weakTests), killedBy(weakTests));
console.log(passOriginal(boundaryTests), killedBy(boundaryTests));
```

It prints `true false` and then `true true`. Both test sets pass on the real code and give full coverage, but only the set with the boundary case (£30 exactly) notices the mutant. Mutation testing is slow, so run it on the most important modules, or on changed code only.

## Flaky tests

A **flaky** test sometimes passes and sometimes fails without any code change. Flaky tests destroy trust: people start re-running failures and ignoring real ones. The usual causes are the same as for intermittent bugs (<Ref to="m-debugging" />): timing (sleeping instead of waiting for a condition), shared state between tests, test order, the real clock and time zone, randomness, and real network calls. Fix them promptly, or quarantine them with an owner and a deadline; never let a suite stay red-sometimes.

## Common mistakes

- **Testing implementation details** (private methods, internal call sequences) so every refactoring breaks tests.
- **Mocking everything**, including domain objects and third-party libraries.
- **Tests with logic**, loops or copied production code in their expected values.
- **Unclear names** such as `test1` or `shouldWork`.
- **In-memory database substitutes** instead of the real database for integration tests.
- **Chasing a coverage number** with tests that assert nothing.
- **Too many end-to-end tests**, slow and flaky, for behaviour a unit test could check.
- **Sleeping** (`await sleep(2000)`) instead of waiting for a condition.
- **Ignoring flaky tests.**

## Practice

**1. (warm-up)** Name the five kinds of test double and say what each does.

<Solution>

Dummy (passed but unused), stub (returns canned answers), spy (records calls for later checking), mock (has expectations and fails if they are not met), fake (a working simplified implementation, such as an in-memory repository).

</Solution>

**2. (warm-up)** Why might 100% line coverage still leave important bugs uncaught?

<Solution>

Coverage only says the lines ran, not that the tests checked the results: a test with no assertions gives full coverage. It also says nothing about boundary values, combinations of conditions or missing code (behaviour that should exist but does not). Mutation testing measures whether tests actually detect changes.

</Solution>

**3. (warm-up)** What are the three steps of the TDD cycle?

<Solution>

Red (write a small failing test and watch it fail), green (write the simplest code that passes it), refactor (clean up while the tests stay green).

</Solution>

**4. (standard)** Write Vitest tests for this function, covering the boundaries:

```ts
export function ticketPrice(age: number): number {
  if (age < 0) throw new RangeError("Age cannot be negative");
  if (age < 5) return 0;
  if (age < 16 || age >= 65) return 450;
  return 900;
}
```

<Solution>

```ts
import { describe, expect, it } from "vitest";
import { ticketPrice } from "./tickets";

describe("ticketPrice", () => {
  it("is free under 5", () => {
    expect(ticketPrice(0)).toBe(0);
    expect(ticketPrice(4)).toBe(0);
  });

  it("charges the child price from 5 to 15", () => {
    expect(ticketPrice(5)).toBe(450);
    expect(ticketPrice(15)).toBe(450);
  });

  it("charges the full price from 16 to 64", () => {
    expect(ticketPrice(16)).toBe(900);
    expect(ticketPrice(64)).toBe(900);
  });

  it("charges the concession price from 65", () => {
    expect(ticketPrice(65)).toBe(450);
  });

  it("rejects a negative age", () => {
    expect(() => ticketPrice(-1)).toThrow(RangeError);
  });
});
```

All five tests pass. Each boundary is tested on both sides (4 and 5, 15 and 16, 64 and 65), which is exactly where an off-by-one bug would hide, and where a mutation tool would make its changes.

</Solution>

**5. (standard)** A test for `OrderService.place` mocks the repository, the mapper, the validator, the price calculator and the event publisher, and checks that each was called in order. What is wrong, and how would you improve it?

<Solution>

It tests the implementation, not the behaviour: any refactoring (merging the mapper into the service, reordering calls) breaks it, and it would still pass if the real pieces did not work together. Use real domain objects and the real price calculator and validator (they are pure logic), an in-memory fake repository and a spy or fake publisher at the boundary. Then assert outcomes: the saved order's contents and total, and the event published. Separately, test the price calculator and validator directly with their own unit tests.

</Solution>

**6. (stretch)** Suggest two properties to test for a function `normaliseEmail(s)` that trims, lower-cases and removes a `+tag` before the `@`.

<Solution>

Idempotence: `normaliseEmail(normaliseEmail(s))` equals `normaliseEmail(s)` for any input. Invariance: adding random whitespace around the input, changing the case of its letters, or adding a `+anything` tag before the `@` does not change the result. Also "never throws on any string", and "the result never contains uppercase letters or surrounding whitespace". A generator of email-like strings (random local parts, tags and domains) makes the tests meaningful.

</Solution>

## Summary

- Tests make change safe; good tests are **fast, isolated, repeatable, self-checking** and focused on **behaviour**.
- The **test pyramid**: many unit tests, fewer integration tests, few end-to-end tests for critical journeys.
- Write tests as **arrange, act, assert**, with behaviour-describing names, boundary cases and no logic.
- **Test doubles**: dummy, stub, spy, mock, fake. Mock only boundaries you own; check outcomes, not internal calls.
- **TDD**: red, green, refactor; strongest for logic and for bug fixes.
- Test infrastructure for real with **Testcontainers**; check service compatibility with **contract tests**.
- **Property-based testing** finds cases you did not think of; **mutation testing** measures whether tests notice changes; coverage only finds gaps.
- Fix or quarantine **flaky** tests at once.
