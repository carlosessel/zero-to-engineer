By the end of this chapter you will store and query data from a .NET service with **Entity Framework Core** (EF Core), Microsoft's **ORM** (object-relational mapper): mapping classes to tables, writing queries in LINQ and seeing the SQL they become, saving changes, loading related data without the N+1 problem, evolving the schema with migrations, and using transactions and optimistic concurrency. <Ref to="sql" />, <Ref to="m-relational" /> and <Ref to="m-schema-design" /> cover the database side; this chapter is how a .NET service talks to it.

## What an ORM does

An **ORM** maps rows in tables to objects in your code, so you work with `Order` objects and LINQ instead of writing every SQL statement by hand. It generates the SQL, tracks which objects changed, and saves them. That saves a great deal of code, but it is not magic: every query becomes SQL, and you must still understand that SQL to make it fast and correct. This chapter shows the SQL each time.

In production you would usually use **PostgreSQL** or **SQL Server**, through the `Npgsql.EntityFrameworkCore.PostgreSQL` or `Microsoft.EntityFrameworkCore.SqlServer` package. The examples here use **SQLite**, a database stored in a single file, so they run anywhere with nothing to install; the EF Core code is the same apart from the `Use...` line.

## A model and a DbContext

You describe the data as **entity** classes, and a **`DbContext`** class that represents a session with the database:

```csharp
#:package Microsoft.EntityFrameworkCore.Sqlite@10.0.15
#:property PublishAot=false

using Microsoft.EntityFrameworkCore;

var options = new DbContextOptionsBuilder<BakeryDb>().UseSqlite("Data Source=model.db").Options;

using (var db = new BakeryDb(options))
{
    db.Database.EnsureDeleted();
    db.Database.EnsureCreated();
    Console.WriteLine(db.Database.GenerateCreateScript().Split("CREATE UNIQUE INDEX")[0].Trim());
}

class BakeryDb(DbContextOptions<BakeryDb> options) : DbContext(options)
{
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Order> Orders => Set<Order>();

    protected override void OnModelCreating(ModelBuilder model)
    {
        model.Entity<Customer>().Property(c => c.Name).HasMaxLength(100);
        model.Entity<Customer>().HasIndex(c => c.Email).IsUnique();
        model.Entity<Order>().Property(o => o.Status).HasConversion<string>().HasMaxLength(20);
    }
}

class Customer
{
    public int Id { get; set; }
    public required string Name { get; set; }
    public required string Email { get; set; }
    public List<Order> Orders { get; set; } = [];
}

class Order
{
    public int Id { get; set; }
    public int CustomerId { get; set; }
    public Customer Customer { get; set; } = null!;
    public int TotalPence { get; set; }
    public OrderStatus Status { get; set; }
}

enum OrderStatus { Placed, Paid, Delivered, Cancelled }
```

It prints the SQL EF Core uses to create the tables (the script continues with the indexes, which the example cuts off):

```text
CREATE TABLE "Customers" (
    "Id" INTEGER NOT NULL CONSTRAINT "PK_Customers" PRIMARY KEY AUTOINCREMENT,
    "Name" TEXT NOT NULL,
    "Email" TEXT NOT NULL
);


CREATE TABLE "Orders" (
    "Id" INTEGER NOT NULL CONSTRAINT "PK_Orders" PRIMARY KEY AUTOINCREMENT,
    "CustomerId" INTEGER NOT NULL,
    "TotalPence" INTEGER NOT NULL,
    "Status" TEXT NOT NULL,
    CONSTRAINT "FK_Orders_Customers_CustomerId" FOREIGN KEY ("CustomerId") REFERENCES "Customers" ("Id") ON DELETE CASCADE
);
```

EF Core works most of this out by **convention**:

- A property called `Id` is the **primary key**, generated by the database.
- `CustomerId` plus the `Customer` **navigation property** make a **foreign key** to `Customers` (and an index on it, in the part of the script not shown); `List<Order> Orders` is the other side of the relationship.
- Non-nullable properties (`required string Name`, `int TotalPence`) become `NOT NULL` columns; `string?` would allow NULL.
- **`OnModelCreating`** adds what conventions cannot guess: the unique index on `Email`, a length limit, storing the enum as text (more readable than numbers, and safe when values are reordered).

`EnsureCreated` builds the schema directly, which is fine for examples and tests; real services use **migrations**, shown later. (SQLite ignores length limits, which is why `Name` shows as plain `TEXT`; PostgreSQL would create `character varying(100)`.)

## Saving and querying

Add objects to the context and call **`SaveChanges`**; query with LINQ, and EF Core translates it to SQL. `ToQueryString()` shows the SQL without running it:

```csharp
#:package Microsoft.EntityFrameworkCore.Sqlite@10.0.15
#:property PublishAot=false

using Microsoft.EntityFrameworkCore;

var options = new DbContextOptionsBuilder<BakeryDb>().UseSqlite("Data Source=query.db").Options;

using (var db = new BakeryDb(options))
{
    db.Database.EnsureDeleted();
    db.Database.EnsureCreated();
    db.Customers.AddRange(
        new Customer { Name = "Ama", Email = "ama@example.com", Orders = { new() { TotalPence = 1250, Status = OrderStatus.Placed }, new() { TotalPence = 3100, Status = OrderStatus.Delivered } } },
        new Customer { Name = "Kofi", Email = "kofi@example.com", Orders = { new() { TotalPence = 450, Status = OrderStatus.Placed } } });
    Console.WriteLine($"saved {db.SaveChanges()} rows");
}

using (var db = new BakeryDb(options))
{
    var query = db.Orders
        .AsNoTracking()
        .Where(o => o.TotalPence > 1000 && o.Status != OrderStatus.Cancelled)
        .OrderByDescending(o => o.TotalPence)
        .Select(o => new { o.Id, Customer = o.Customer.Name, o.TotalPence });

    Console.WriteLine(query.ToQueryString());
    foreach (var row in query.ToList()) Console.WriteLine(row);

    var totals = db.Orders
        .GroupBy(o => o.Customer.Name)
        .Select(g => new { Customer = g.Key, Orders = g.Count(), Revenue = g.Sum(o => o.TotalPence) })
        .OrderBy(x => x.Customer)
        .ToList();
    foreach (var t in totals) Console.WriteLine(t);

    var page = db.Customers.OrderBy(c => c.Id).Skip(1).Take(1).Select(c => c.Email).ToList();
    Console.WriteLine(string.Join(", ", page));
}

class BakeryDb(DbContextOptions<BakeryDb> options) : DbContext(options)
{
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Order> Orders => Set<Order>();
    protected override void OnModelCreating(ModelBuilder model) =>
        model.Entity<Order>().Property(o => o.Status).HasConversion<string>();
}

class Customer
{
    public int Id { get; set; }
    public required string Name { get; set; }
    public required string Email { get; set; }
    public List<Order> Orders { get; set; } = [];
}

class Order
{
    public int Id { get; set; }
    public int CustomerId { get; set; }
    public Customer Customer { get; set; } = null!;
    public int TotalPence { get; set; }
    public OrderStatus Status { get; set; }
}

enum OrderStatus { Placed, Paid, Delivered, Cancelled }
```

It prints:

```text
saved 5 rows
SELECT "o"."Id", "c"."Name" AS "Customer", "o"."TotalPence"
FROM "Orders" AS "o"
INNER JOIN "Customers" AS "c" ON "o"."CustomerId" = "c"."Id"
WHERE "o"."TotalPence" > 1000 AND "o"."Status" <> 'Cancelled'
ORDER BY "o"."TotalPence" DESC
{ Id = 2, Customer = Ama, TotalPence = 3100 }
{ Id = 1, Customer = Ama, TotalPence = 1250 }
{ Customer = Ama, Orders = 2, Revenue = 4350 }
{ Customer = Kofi, Orders = 1, Revenue = 450 }
kofi@example.com
```

<Walkthrough name="be-data-efcore-linq-to-sql" />

- `SaveChanges` inserted two customers and three orders (5 rows), filling in the foreign keys from the object graph.
- The LINQ became one SQL query with a `JOIN`, because the projection used `o.Customer.Name`. Filtering, sorting, grouping and paging all run **in the database**; only the results come back.
- **`Select`** to just the columns you need (a **projection**) is the most effective way to keep queries fast.
- **`AsNoTracking`** tells EF Core not to track the results for changes: faster, and right for read-only queries.
- Use the async versions (`ToListAsync`, `SaveChangesAsync`, `FirstOrDefaultAsync`) in services, passing the request's `CancellationToken` (<Ref to="cs-errors-async" />); the examples use the synchronous ones to stay short.
- A LINQ expression EF Core cannot translate to SQL fails with an error, rather than silently loading every row into memory.

## Updating and deleting

A context **tracks** the entities it loads. Change their properties and `SaveChanges` writes just the changes. For bulk changes, **`ExecuteUpdate`** and **`ExecuteDelete`** run one SQL statement without loading anything:

```csharp
#:package Microsoft.EntityFrameworkCore.Sqlite@10.0.15
#:property PublishAot=false

using Microsoft.EntityFrameworkCore;

var options = new DbContextOptionsBuilder<BakeryDb>().UseSqlite("Data Source=update.db").Options;
using (var db = new BakeryDb(options))
{
    db.Database.EnsureDeleted();
    db.Database.EnsureCreated();
    db.Orders.AddRange(new Order { TotalPence = 1250, Status = "placed" }, new Order { TotalPence = 450, Status = "placed" }, new Order { TotalPence = 990, Status = "placed" });
    db.SaveChanges();
}

using (var db = new BakeryDb(options))
{
    var order = db.Orders.Single(o => o.Id == 1);
    order.Status = "paid";
    Console.WriteLine(db.Entry(order).State);
    db.SaveChanges();
    Console.WriteLine(db.Entry(order).State);

    int cancelled = db.Orders.Where(o => o.Status == "placed" && o.TotalPence < 1000)
        .ExecuteUpdate(s => s.SetProperty(o => o.Status, "cancelled"));
    Console.WriteLine($"cancelled {cancelled}");

    int deleted = db.Orders.Where(o => o.Status == "cancelled").ExecuteDelete();
    Console.WriteLine($"deleted {deleted}");
}

using (var db = new BakeryDb(options))
{
    foreach (var o in db.Orders.AsNoTracking()) Console.WriteLine($"{o.Id} {o.Status}");
}

class BakeryDb(DbContextOptions<BakeryDb> options) : DbContext(options)
{
    public DbSet<Order> Orders => Set<Order>();
}

class Order
{
    public int Id { get; set; }
    public int TotalPence { get; set; }
    public required string Status { get; set; }
}
```

It prints `Modified`, `Unchanged`, `cancelled 2`, `deleted 2`, and then `1 paid`: the one order left. Note that `ExecuteUpdate` and `ExecuteDelete` run immediately and bypass change tracking.

## Related data and the N+1 problem

Loading a list and then touching a related entity for each item can fire one query for the list plus one per item: the **N+1 problem**, a classic cause of slow pages (<Ref to="m-performance" />). EF Core does not load related data unless you ask, so the fix is to ask in the first query, with **`Include`** or a projection. Here a command interceptor counts the SQL statements:

```csharp
#:package Microsoft.EntityFrameworkCore.Sqlite@10.0.15
#:property PublishAot=false

using System.Data.Common;
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Diagnostics;

var counter = new CommandCounter();
var options = new DbContextOptionsBuilder<BakeryDb>().UseSqlite("Data Source=nplus1.db").AddInterceptors(counter).Options;

using (var db = new BakeryDb(options))
{
    db.Database.EnsureDeleted();
    db.Database.EnsureCreated();
    for (var i = 1; i <= 20; i++)
        db.Customers.Add(new Customer { Name = $"Customer {i}", Orders = { new() { TotalPence = 100 * i }, new() { TotalPence = 50 } } });
    db.SaveChanges();
}

using (var db = new BakeryDb(options))
{
    counter.Count = 0;
    long total = 0;
    foreach (var c in db.Customers.ToList())
        total += db.Orders.Where(o => o.CustomerId == c.Id).Sum(o => o.TotalPence);
    Console.WriteLine($"one query per customer: {counter.Count} queries, total {total}");

    counter.Count = 0;
    var withOrders = db.Customers.Include(c => c.Orders).AsNoTracking().ToList();
    Console.WriteLine($"Include: {counter.Count} query, total {withOrders.Sum(c => c.Orders.Sum(o => o.TotalPence))}");

    counter.Count = 0;
    var summary = db.Customers.Select(c => new { c.Name, Total = c.Orders.Sum(o => o.TotalPence) }).ToList();
    Console.WriteLine($"projection: {counter.Count} query, total {summary.Sum(s => s.Total)}");
}

class CommandCounter : DbCommandInterceptor
{
    public int Count;
    public override DbDataReader ReaderExecuted(DbCommand command, CommandExecutedEventData data, DbDataReader result)
    {
        Count++;
        return result;
    }
}

class BakeryDb(DbContextOptions<BakeryDb> options) : DbContext(options)
{
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Order> Orders => Set<Order>();
}

class Customer
{
    public int Id { get; set; }
    public required string Name { get; set; }
    public List<Order> Orders { get; set; } = [];
}

class Order
{
    public int Id { get; set; }
    public int CustomerId { get; set; }
    public int TotalPence { get; set; }
}
```

It prints `one query per customer: 21 queries, total 22000`, then `Include: 1 query` and `projection: 1 query`, both with the same total. With 20 customers the difference is small; with 2,000 customers and a database 2 ms away, the loop takes four seconds. Prefer projections for read-only results; use `Include` when you need the full entities to change them. Avoid turning on **lazy loading**, which hides exactly this problem behind innocent-looking property access.

## Migrations

Your schema will change: new tables, new columns, new indexes. **Migrations** record each change as code, in order, so every environment's database can be brought to the same version. With the EF Core tools (`dotnet tool install --global dotnet-ef`) in a project:

```bash
dotnet ef migrations add AddOrderNote
dotnet ef migrations script --idempotent --output migrate.sql
dotnet ef database update
```

- `migrations add` compares your model with the last migration and writes a new migration class with `Up` (apply) and `Down` (undo) methods. Commit it with the code change, and **review it** like code: check it does what you expect.
- `migrations script --idempotent` produces a SQL script that can be run safely against any version of the database; many teams apply this script in their deployment pipeline, rather than letting the application change its own schema at start-up.
- `database update` applies pending migrations directly, which is handy on your own machine.

Design changes that are safe while the old version of the service is still running: add a nullable column first, deploy, backfill, then make it required in a later migration (**expand and contract**, <Ref to="m-delivery" />).

## Transactions and concurrency

**`SaveChanges` is a transaction**: either every change in it is saved or none is. To group several `SaveChanges` calls, or a mix of EF Core and raw SQL, start one explicitly. And to stop two people overwriting each other's changes, mark a **concurrency token**: EF Core adds it to the `WHERE` clause of updates and refuses if someone else changed the row first (**optimistic concurrency**, <Ref to="m-relational" />):

```csharp
#:package Microsoft.EntityFrameworkCore.Sqlite@10.0.15
#:property PublishAot=false

using Microsoft.EntityFrameworkCore;

var options = new DbContextOptionsBuilder<BakeryDb>().UseSqlite("Data Source=tx.db").Options;
using (var db = new BakeryDb(options))
{
    db.Database.EnsureDeleted();
    db.Database.EnsureCreated();
    db.Stock.Add(new StockItem { Sku = "RYE-400", Quantity = 5 });
    db.SaveChanges();
}

using (var db = new BakeryDb(options))
{
    using var tx = db.Database.BeginTransaction();
    var item = db.Stock.Single(s => s.Sku == "RYE-400");
    item.Quantity -= 2;
    item.Version++;
    db.SaveChanges();
    db.Orders.Add(new Order { Sku = "RYE-400", Quantity = 2 });
    db.SaveChanges();
    tx.Commit();
    Console.WriteLine($"committed: stock {item.Quantity}, orders {db.Orders.Count()}");
}

using var shop = new BakeryDb(options);
using var website = new BakeryDb(options);
var inShop = shop.Stock.Single(s => s.Sku == "RYE-400");
var online = website.Stock.Single(s => s.Sku == "RYE-400");

inShop.Quantity -= 3;
inShop.Version++;
shop.SaveChanges();

online.Quantity -= 3;
online.Version++;
try
{
    website.SaveChanges();
}
catch (DbUpdateConcurrencyException)
{
    Console.WriteLine("website: someone else changed the stock first; reload and try again");
}

using var check = new BakeryDb(options);
Console.WriteLine($"stock now {check.Stock.Single().Quantity}");

class BakeryDb(DbContextOptions<BakeryDb> options) : DbContext(options)
{
    public DbSet<StockItem> Stock => Set<StockItem>();
    public DbSet<Order> Orders => Set<Order>();
    protected override void OnModelCreating(ModelBuilder model) =>
        model.Entity<StockItem>().Property(s => s.Version).IsConcurrencyToken();
}

class StockItem
{
    public int Id { get; set; }
    public required string Sku { get; set; }
    public int Quantity { get; set; }
    public int Version { get; set; }
}

class Order
{
    public int Id { get; set; }
    public required string Sku { get; set; }
    public int Quantity { get; set; }
}
```

It prints `committed: stock 3, orders 1`, then the website's refusal, then `stock now 0`. Without the token, both saves would have succeeded: each had loaded 3 loaves and wrote back 0, so six loaves were sold from a stock of three and nothing noticed. SQL Server can generate the token for you with a `rowversion` column (`[Timestamp]`), and PostgreSQL with its `xmin` system column; this example increments a version number by hand because SQLite has neither.

## In an ASP.NET Core service

Register the context with the connection string from configuration; it is **scoped**, one per request (<Ref to="be-dependency-injection" />), and handlers receive it like any service:

```csharp
builder.Services.AddDbContext<BakeryDb>(options =>
    options.UseNpgsql(builder.Configuration.GetConnectionString("Bakery")));

app.MapGet("/orders/{id:int}", async Task<Results<Ok<OrderDto>, NotFound>> (int id, BakeryDb db, CancellationToken ct) =>
    await db.Orders
        .Where(o => o.Id == id)
        .Select(o => new OrderDto(o.Id, o.Customer.Name, o.TotalPence))
        .FirstOrDefaultAsync(ct) is { } order
        ? TypedResults.Ok(order)
        : TypedResults.NotFound());
```

The connection string (`ConnectionStrings:Bakery`, or the environment variable `ConnectionStrings__Bakery`) holds the password, so it comes from user secrets or the environment, never from committed files. Return DTOs, not entities, from endpoints, and keep queries in services or repositories as the service grows.

### Raw SQL, safely

When LINQ cannot express a query, EF Core runs SQL you write. **`FromSql`** with an interpolated string turns each `{value}` into a **parameter**, so it is safe from SQL injection; building SQL by concatenating strings is not (<Ref to="m-appsec" />):

```csharp
var sku = "RYE-400";
var safe = db.Stock.FromSql($"SELECT * FROM Stock WHERE Sku = {sku}").ToList();
// Never: db.Stock.FromSqlRaw("SELECT * FROM Stock WHERE Sku = '" + sku + "'")
```

## Common mistakes

- **N+1 queries** from loops over related data, or from lazy loading.
- **Loading whole entities** (or whole tables) when a projection of three columns would do.
- **Tracking read-only queries**; use `AsNoTracking`.
- **Sharing a `DbContext`** between threads or requests, or registering it as a singleton.
- **Calling `ToList()` too early**, so filtering happens in memory instead of in SQL.
- **Unreviewed migrations**, or schema changes that break the version still running.
- **Building SQL strings by concatenation.**

## Practice

**1. (warm-up)** What SQL will EF Core run for `db.Orders.Where(o => o.Status == OrderStatus.Paid).Count()`, roughly, and how many rows come back to the application?

<Solution>

Roughly `SELECT COUNT(*) FROM "Orders" AS "o" WHERE "o"."Status" = 'Paid'` (with the enum stored as text). One row with one number comes back; the counting happens in the database.

</Solution>

**2. (warm-up)** Why is `db.Orders.ToList().Where(o => o.TotalPence > 1000)` much worse than `db.Orders.Where(o => o.TotalPence > 1000).ToList()`?

<Solution>

`ToList()` runs the query, so the first version loads **every** order from the database and then filters in memory; the second sends the `WHERE` to the database and loads only the matching rows. With a million orders, the first is slow and uses a lot of memory.

</Solution>

**3. (standard)** Using the customers-and-orders model from this chapter, write a query that returns each customer's name and the date-independent count of their orders over £20, only for customers with at least one such order, using one SQL query. Print its SQL.

<Solution>

```csharp
#:package Microsoft.EntityFrameworkCore.Sqlite@10.0.15
#:property PublishAot=false

using Microsoft.EntityFrameworkCore;

var options = new DbContextOptionsBuilder<BakeryDb>().UseSqlite("Data Source=practice.db").Options;
using var db = new BakeryDb(options);
db.Database.EnsureDeleted();
db.Database.EnsureCreated();
db.Customers.AddRange(
    new Customer { Name = "Ama", Orders = { new() { TotalPence = 2500 }, new() { TotalPence = 3100 }, new() { TotalPence = 900 } } },
    new Customer { Name = "Kofi", Orders = { new() { TotalPence = 450 } } });
db.SaveChanges();

var query = db.Customers
    .Select(c => new { c.Name, Big = c.Orders.Count(o => o.TotalPence > 2000) })
    .Where(x => x.Big > 0);
foreach (var row in query) Console.WriteLine(row);
Console.WriteLine(query.ToQueryString().Contains("COUNT(*)"));

class BakeryDb(DbContextOptions<BakeryDb> options) : DbContext(options)
{
    public DbSet<Customer> Customers => Set<Customer>();
}

class Customer
{
    public int Id { get; set; }
    public required string Name { get; set; }
    public List<Order> Orders { get; set; } = [];
}

class Order
{
    public int Id { get; set; }
    public int CustomerId { get; set; }
    public int TotalPence { get; set; }
}
```

It prints **`{ Name = Ama, Big = 2 }`** and **True**: the count is a subquery inside the single SQL statement, so Kofi is filtered out by the database.

</Solution>

**4. (stretch)** Two staff members edit the same product's price at the same time. Without a concurrency token, what happens? With one, what should the API return to the second person, and what should the client do?

<Solution>

Without a token, both updates succeed and the second silently overwrites the first ("last write wins"); the first person's change is lost without anyone knowing. With a token, the second `SaveChanges` throws `DbUpdateConcurrencyException`; the API should catch it and return **409 Conflict** (or 412 Precondition Failed if the client sent an `If-Match` ETag), and the client should reload the current product, show the other person's change, and let the user decide whether to apply theirs on top.

</Solution>

## Summary

- An **ORM** maps tables to classes; EF Core's **`DbContext`** is a session with the database and **`DbSet<T>`** its tables. Conventions find keys and relationships; `OnModelCreating` adds the rest.
- LINQ queries become SQL (see it with **`ToQueryString`**); filter, sort, group and page in the database; **project** with `Select`; use **`AsNoTracking`** for reads and the async methods in services.
- **`SaveChanges`** writes tracked changes in one transaction; **`ExecuteUpdate`** and **`ExecuteDelete`** run bulk statements.
- Avoid **N+1** with `Include` or projections; avoid lazy loading.
- **Migrations** version the schema; review them and apply them in deployment, in expand-and-contract steps.
- **Concurrency tokens** give optimistic concurrency. Register the context as scoped; use parameterised `FromSql` for raw SQL.
