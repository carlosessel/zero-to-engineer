## What they are good at

Explaining unfamiliar code and error messages, drafting routine code and tests, translating between languages, suggesting approaches, and reviewing your work for mistakes.

## Where they fail

They produce confident code that is subtly wrong, call functions that do not exist, miss requirements you did not state, introduce security holes, and do not know your codebase unless shown it. They do not carry responsibility. You do.

## Rules for using them well

- **Never merge code you cannot explain line by line.**
- **Give context**: what the code is for, the constraints, the surrounding code, and an example of the result you want.
- **Ask for a plan first** on anything large, then build in small steps you can check.
- **Test everything it writes.** Your tests are how you verify a machine’s work.
- **Review for security** especially: input validation, access checks, secrets.
- **Do not paste secrets or private data** into tools your employer has not approved.

## While you are learning

If the assistant writes your exercises, you learn nothing, and the fundamentals are exactly what let you judge its output later. Write the code yourself first. Then ask the assistant to review it, explain an error, or show another approach. Use it as a tutor.

The engineers who do well alongside these tools are the ones who can specify a problem precisely, read code critically, design systems, and take responsibility for results. Those are the skills this course trains.
