By the end of this chapter you will design database schemas that keep data correct by construction (normalised tables, the right keys and types, and constraints that reject bad data), know when to deliberately denormalise for speed, and change a schema in production without downtime using the expand-and-contract method. Data usually outlives the code that writes it, so schema mistakes are among the most expensive to fix.

## Normalisation

**Normalisation** organises tables so that each fact is stored **once**. When the same fact is stored in several rows, they can disagree. Take a single wide table of order lines that repeats each customer's details on every line:

```python
import sqlite3

db = sqlite3.connect(":memory:")


def main():
    db.execute("CREATE TABLE order_rows (order_id INTEGER, customer_email TEXT, customer_postcode TEXT, sku TEXT, qty INTEGER)")
    db.executemany(
        "INSERT INTO order_rows VALUES (?, ?, ?, ?, ?)",
        [(1, "ama@example.com", "LS1 4AP", "RYE-400", 2), (2, "ama@example.com", "LS1 4AP", "JAM-STR", 1), (3, "kofi@example.com", "M1 1AE", "RYE-400", 1)],
    )
    db.execute("UPDATE order_rows SET customer_postcode = 'LS6 2QT' WHERE order_id = 2")
    print("Ama's postcodes:", [r[0] for r in db.execute("SELECT DISTINCT customer_postcode FROM order_rows WHERE customer_email = 'ama@example.com'")])

    db.execute("CREATE TABLE customers (id INTEGER PRIMARY KEY, email TEXT NOT NULL UNIQUE, postcode TEXT NOT NULL)")
    db.execute("CREATE TABLE orders (id INTEGER PRIMARY KEY, customer_id INTEGER NOT NULL REFERENCES customers(id))")
    db.execute("CREATE TABLE order_lines (order_id INTEGER NOT NULL REFERENCES orders(id), sku TEXT NOT NULL, qty INTEGER NOT NULL CHECK (qty > 0), PRIMARY KEY (order_id, sku))")
    db.execute("INSERT INTO customers (email, postcode) SELECT DISTINCT customer_email, MIN(customer_postcode) FROM order_rows GROUP BY customer_email")
    db.execute("INSERT INTO orders SELECT DISTINCT r.order_id, c.id FROM order_rows r JOIN customers c ON c.email = r.customer_email")
    db.execute("INSERT INTO order_lines SELECT order_id, sku, qty FROM order_rows")
    db.execute("UPDATE customers SET postcode = 'LS6 2QT' WHERE email = 'ama@example.com'")
    rows = db.execute(
        "SELECT o.id, c.email, c.postcode, l.sku, l.qty FROM orders o JOIN customers c ON c.id = o.customer_id JOIN order_lines l ON l.order_id = o.id ORDER BY o.id"
    ).fetchall()
    for row in rows:
        print(row)


main()
```

It prints `Ama's postcodes: ['LS1 4AP', 'LS6 2QT']`: updating one row of the wide table left Ama with two postcodes, an **update anomaly**. The same design has an **insertion anomaly** (you cannot record a customer who has not ordered yet) and a **deletion anomaly** (deleting Kofi's only order loses his postcode). In the normalised version, the postcode lives in one row of `customers`; one update changes it everywhere, and the joined result shows `LS6 2QT` on both of Ama's orders.

The **normal forms** formalise this:

- **First normal form (1NF)**: each column holds one value (no comma-separated lists of SKUs in one column), and each row is identifiable.
- **Second normal form (2NF)**: every non-key column depends on the **whole** key. In a table keyed by (order, SKU), the customer's email depends only on the order, so it belongs in `orders`.
- **Third normal form (3NF)**: non-key columns depend on the key and **nothing but the key**. A customer's town depends on their postcode, not directly on the customer, so in a strict design it would come from an address table.

A popular summary: every column should depend on "the key, the whole key, and nothing but the key". In practice, aim for third normal form by default, and break it only deliberately.

## Keys

Every table needs a **primary key**. Two choices:

- A **natural key** is a real-world identifier: an email, an ISBN, a country code. It is meaningful, but real-world identifiers change (people change emails) and are sometimes not as unique as they seem.
- A **surrogate key** is a meaningless identifier generated by the system: an auto-increment integer or a UUID. It never needs to change, so use one for most entities, and add a `UNIQUE` constraint on any natural key you rely on.

Integers are compact and fast. **UUIDs** can be generated anywhere (by clients, by many services) without coordination and do not reveal how many rows you have, but random UUIDs (version 4) scatter inserts across a B-tree index, which slows writes on large tables. **UUID version 7** (standardised in RFC 9562, 2024) starts with a timestamp, so new ids sort roughly in time order and index well; prefer it when you want UUIDs.

## Types

Choose types that say exactly what the data is:

- **Money**: never floating point (<Ref to="m-data-representation" />). Use `NUMERIC`/`DECIMAL`, or an integer number of the smallest unit (pence), and store the currency alongside.
- **Points in time**: `timestamptz` in PostgreSQL (stored as UTC, converted on display), `datetimeoffset` in SQL Server. Plain "timestamp without time zone" is a common source of bugs when servers and users are in different zones.
- **Fixed sets of values**: a `CHECK` constraint, an enum type, or a small lookup table with a foreign key.
- **Text**: limit length where the domain has a limit (a postcode), and compare case-insensitively where appropriate (PostgreSQL's `citext`, or a unique index on `LOWER(email)`).
- **JSON columns** (`jsonb` in PostgreSQL) suit genuinely variable data: settings, provider payloads, attributes that differ per product type. They are not a way to avoid designing a schema: the database cannot enforce relationships inside JSON, and querying it is harder.

## Constraints: let the database say no

Application code has bugs, there is usually more than one application or script writing to a database, and someone will eventually run a manual fix in production. **Constraints** are rules the database itself enforces on every write, whoever makes it:

```python
import sqlite3

db = sqlite3.connect(":memory:", isolation_level=None)


def attempt(label, sql, params=()):
    try:
        db.execute(sql, params)
        print(f"{label}: accepted")
    except sqlite3.IntegrityError as e:
        print(f"{label}: rejected ({e})")


def main():
    db.execute("PRAGMA foreign_keys = ON")
    db.execute("CREATE TABLE customers (id INTEGER PRIMARY KEY, email TEXT NOT NULL UNIQUE)")
    db.execute(
        "CREATE TABLE subscriptions (id INTEGER PRIMARY KEY, customer_id INTEGER NOT NULL REFERENCES customers(id), "
        "plan TEXT NOT NULL CHECK (plan IN ('weekly', 'monthly')), status TEXT NOT NULL CHECK (status IN ('active', 'cancelled')), "
        "pence INTEGER NOT NULL CHECK (pence > 0))"
    )
    db.execute("CREATE UNIQUE INDEX one_active_subscription ON subscriptions (customer_id) WHERE status = 'active'")
    db.execute("INSERT INTO customers (email) VALUES ('ama@example.com')")

    attempt("first active subscription", "INSERT INTO subscriptions (customer_id, plan, status, pence) VALUES (1, 'weekly', 'active', 1200)")
    attempt("second active subscription", "INSERT INTO subscriptions (customer_id, plan, status, pence) VALUES (1, 'monthly', 'active', 4000)")
    attempt("old cancelled subscription", "INSERT INTO subscriptions (customer_id, plan, status, pence) VALUES (1, 'monthly', 'cancelled', 4000)")
    attempt("unknown customer", "INSERT INTO subscriptions (customer_id, plan, status, pence) VALUES (99, 'weekly', 'active', 1200)")
    attempt("misspelt plan", "INSERT INTO subscriptions (customer_id, plan, status, pence) VALUES (1, 'weakly', 'cancelled', 1200)")
    attempt("duplicate email", "INSERT INTO customers (email) VALUES ('ama@example.com')")


main()
```

It prints:

```text
first active subscription: accepted
second active subscription: rejected (UNIQUE constraint failed: subscriptions.customer_id)
old cancelled subscription: accepted
unknown customer: rejected (FOREIGN KEY constraint failed)
misspelt plan: rejected (CHECK constraint failed: plan IN ('weekly', 'monthly'))
duplicate email: rejected (UNIQUE constraint failed: customers.email)
```

Each constraint expresses a business rule the database now guarantees:

- `NOT NULL`: the value is required.
- `UNIQUE`: no duplicates, which also closes the race where two requests both check "is this email taken?" and both insert (<Ref to="m-threads-locks" />).
- `CHECK`: the value is in range or one of a set.
- `FOREIGN KEY`: the referenced row exists (and, with `ON DELETE`, what happens when it is deleted). SQLite needs `PRAGMA foreign_keys = ON`; other databases enforce them always.
- A **partial unique index** (`WHERE status = 'active'`) expresses "at most one active subscription per customer" while allowing any number of cancelled ones. PostgreSQL also has **exclusion constraints** for rules such as "no two bookings of the same room overlap in time".

Validate in the application too, for friendly error messages (<Ref to="m-errors" />); the constraints are the safety net that keeps the data correct when the application gets it wrong.

## Common modelling patterns

- **One-to-many**: a foreign key on the "many" side (`orders.customer_id`).
- **Many-to-many**: a **join table** with two foreign keys and a composite primary key (`product_tags (product_id, tag_id)`), plus any facts about the relationship (when the tag was added).
- **Audit columns**: `created_at`, `updated_at`, and who made the change. For a full history, an append-only history table or event sourcing (<Ref to="m-architecture" />).
- **Soft delete** (`deleted_at` instead of deleting): keeps history and allows undo, but every query must remember to exclude deleted rows, unique constraints must allow a deleted duplicate (a partial index again), and privacy law may require real deletion. Prefer archiving to a separate table when you can.
- **Avoid polymorphic associations** (a `commentable_type` and `commentable_id` pair that can point at several tables): the database cannot enforce the reference. Use separate foreign key columns or separate join tables.

## Denormalising deliberately

Normalised schemas need joins, and on very hot read paths joins or aggregations can be too slow. **Denormalisation** stores derived or duplicated data on purpose:

- a counter column (`orders_count` on customers) instead of counting each time;
- a copy of data at a point in time that *should* not change later, such as the price and product name on an order line (if the product's price changes next week, the old order must still show what the customer paid; that is not duplication, it is a different fact);
- a **materialised view** or a read model (<Ref to="m-architecture" />) shaped for one screen or report;
- a search index or cache (<Ref to="m-caching" />).

Every denormalised copy needs a defined way to stay correct: updated in the same transaction, refreshed on a schedule, or rebuilt from events, and a known tolerance for how stale it may be. Measure before denormalising (<Ref to="m-performance" />); a good index often makes it unnecessary.

## Migrations

Schemas change as the product changes. A **migration** is a versioned, scripted change to the schema (and sometimes the data), kept in the repository and applied in order by a tool that records which ones have run: Flyway or Liquibase (Java), EF Core migrations (.NET), Prisma, Knex or node-pg-migrate (Node.js), Alembic (Python). Never change a production schema by hand.

```sql
-- V12__add_full_name_to_customers.sql (Flyway naming: version, two underscores, description)
ALTER TABLE customers ADD COLUMN full_name text;
```

Rules: migrations are **immutable** once applied anywhere shared (fix mistakes with a new migration); they run automatically in the deployment pipeline; and every environment, including developers' machines, is built from them.

### Changing a schema without downtime

During a deployment, the old and new versions of your application run at the same time (rolling deployments replace servers one by one), and either may need to be rolled back. So every schema change must work with **both** versions. Renaming a column in one step breaks every running copy of the old code instantly.

The safe method is **expand and contract** (also called parallel change): first add the new structure alongside the old, move code and data over in steps, and only then remove the old. Renaming `customers.name` to `full_name`:

```python
import sqlite3

db = sqlite3.connect(":memory:", isolation_level=None)


def columns():
    return [row[1] for row in db.execute("PRAGMA table_info(customers)")]


def old_app_signs_up(name):
    db.execute("INSERT INTO customers (name) VALUES (?)", (name,))


def bridging_app_signs_up(name):
    db.execute("INSERT INTO customers (name, full_name) VALUES (?, ?)", (name, name))


def new_app_reads():
    return [row[0] for row in db.execute("SELECT full_name FROM customers ORDER BY id")]


def backfill(batch_size):
    batches = 0
    while True:
        changed = db.execute(
            "UPDATE customers SET full_name = name WHERE id IN (SELECT id FROM customers WHERE full_name IS NULL LIMIT ?)", (batch_size,)
        ).rowcount
        if changed == 0:
            return batches
        batches += 1


def main():
    db.execute("CREATE TABLE customers (id INTEGER PRIMARY KEY, name TEXT NOT NULL)")
    for i in range(1, 8):
        old_app_signs_up(f"Customer {i}")

    db.execute("ALTER TABLE customers ADD COLUMN full_name TEXT")
    print("1 expand:", columns())
    old_app_signs_up("Ama Mensah")
    print("  old code still works; rows missing full_name:", db.execute("SELECT COUNT(*) FROM customers WHERE full_name IS NULL").fetchone()[0])

    bridging_app_signs_up("Kofi Boateng")
    print("2 deploy code that writes both columns")

    print("3 backfill in batches of 3:", backfill(3), "batches")

    print("4 deploy code that reads full_name:", new_app_reads()[-2:])

    db.execute("ALTER TABLE customers DROP COLUMN name")
    print("5 contract:", columns())


main()
```

It prints each step: the column is added (`['id', 'name', 'full_name']`) and the old code keeps working; new code writes both; the 8 rows still missing `full_name` are filled in 3 batches; the newest code reads `full_name` (`['Ama Mensah', 'Kofi Boateng']`); finally the old column is dropped (`['id', 'full_name']`). Each step is a separate deployment, and at every moment the running code and the schema agree. Rolling back any single step is safe.

<Walkthrough name="m-schema-design-expand-contract" />

The same pattern handles other risky changes:

- **Adding a required column**: add it as nullable (or with a default), backfill, then add `NOT NULL` once every row has a value.
- **Splitting or moving a table**: write to both, backfill, switch reads, stop writing the old, drop it.
- **Backfills** run in **batches** with short transactions, so they do not lock the table or flood replication (<Ref to="m-replication-partitioning" />).
- **Indexes on large tables**: build them without blocking writes (`CREATE INDEX CONCURRENTLY` in PostgreSQL, `ONLINE = ON` in SQL Server).
- **Know which `ALTER TABLE` operations lock the table** in your database, and for how long. Setting a short lock timeout (`SET lock_timeout = '5s'` in PostgreSQL) makes a migration fail fast instead of queueing behind a long query and blocking everything after it.

## Common mistakes

- **Storing the same fact in many rows** without a plan to keep them in step.
- **Comma-separated values** in one column.
- **Floating-point money** and time zones left to chance.
- **No constraints**, trusting application code alone.
- **Natural keys that change** used as primary keys.
- **One-step renames and drops** that break the running application.
- **Huge single-transaction backfills** that lock tables.
- **Editing old migrations** after they have run elsewhere.

## Practice

**1. (warm-up)** Name the three anomalies normalisation prevents, with an example of each in a single wide orders table.

<Solution>

Update anomaly (changing a customer's postcode in one row but not others leaves conflicting postcodes); insertion anomaly (you cannot store a new customer until they place an order); deletion anomaly (deleting a customer's only order deletes everything known about them).

</Solution>

**2. (warm-up)** Why should an order line store the price the customer paid, even though products have their own price column?

<Solution>

Because they are different facts: the product's current price can change, but the price on a past order must stay what the customer was charged (for invoices, refunds and accounting). Copying it at the time of the order is correct modelling, not harmful duplication.

</Solution>

**3. (warm-up)** Why use UUID version 7 rather than version 4 for primary keys on a large table?

<Solution>

Version 7 starts with a timestamp, so new ids are roughly increasing and are inserted near the end of the B-tree index, keeping writes fast and the index compact. Random version 4 ids land all over the index, causing many page splits and cache misses on large tables.

</Solution>

**4. (standard)** Write a SQLite schema for products and tags (many-to-many) that prevents a product having the same tag twice and refuses tags for products that do not exist. Show both rules working.

<Solution>

```python
import sqlite3

db = sqlite3.connect(":memory:", isolation_level=None)


def main():
    db.execute("PRAGMA foreign_keys = ON")
    db.execute("CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT NOT NULL)")
    db.execute("CREATE TABLE tags (id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE)")
    db.execute(
        "CREATE TABLE product_tags (product_id INTEGER NOT NULL REFERENCES products(id), "
        "tag_id INTEGER NOT NULL REFERENCES tags(id), PRIMARY KEY (product_id, tag_id))"
    )
    db.execute("INSERT INTO products (name) VALUES ('Rye loaf')")
    db.execute("INSERT INTO tags (name) VALUES ('vegan'), ('wholegrain')")
    db.execute("INSERT INTO product_tags VALUES (1, 1), (1, 2)")
    for row in [(1, 1), (5, 1)]:
        try:
            db.execute("INSERT INTO product_tags VALUES (?, ?)", row)
        except sqlite3.IntegrityError as e:
            print(row, "rejected:", e)
    print(db.execute("SELECT p.name, group_concat(t.name, ', ') FROM product_tags pt JOIN products p ON p.id = pt.product_id JOIN tags t ON t.id = pt.tag_id GROUP BY p.id").fetchall())


main()
```

It prints **(1, 1) rejected: UNIQUE constraint failed: product_tags.product_id, product_tags.tag_id**, then **(5, 1) rejected: FOREIGN KEY constraint failed**, then **[('Rye loaf', 'vegan, wholegrain')]**.

</Solution>

**5. (standard)** Plan a zero-downtime migration that makes `customers.phone` required, on a table where 3% of rows have no phone.

<Solution>

First decide what the missing phones should become (a placeholder is usually wrong; perhaps the requirement should apply only to new customers, which is a product decision). Then: (1) deploy application code that always supplies a phone for new and updated customers; (2) backfill the existing nulls in batches with whatever the agreed values are; (3) add the constraint without a long lock (in PostgreSQL, add `CHECK (phone IS NOT NULL) NOT VALID`, then `VALIDATE CONSTRAINT`, which does not block writes, and optionally convert it to `SET NOT NULL`); (4) only then rely on it in code.

</Solution>

**6. (stretch)** A team renamed a column in one migration and deployed. For four minutes, half the servers threw errors. Explain why, and how expand and contract would have avoided it.

<Solution>

The migration ran before or during the rolling deployment: servers still running the old code queried the old column name, which no longer existed, until each was replaced. With expand and contract, the first deployment adds the new column while keeping the old; later deployments move writes and reads over and backfill; the old column is dropped only after no running code uses it. At every moment, every running version works with the current schema, and any step can be rolled back.

</Solution>

## Summary

- **Normalise** so each fact is stored once (aim for **third normal form**); this prevents update, insertion and deletion anomalies.
- Use **surrogate keys** (integers or UUIDv7) plus `UNIQUE` constraints on natural keys.
- Choose precise **types**: exact money, time zone-aware timestamps, constrained sets; use JSON only for genuinely variable data.
- **Constraints** (`NOT NULL`, `UNIQUE`, `CHECK`, foreign keys, partial unique indexes) make the database reject bad data from any source.
- **Denormalise deliberately**, with a defined way to keep copies correct.
- Change schemas with versioned, immutable **migrations**, and without downtime by **expand and contract**: add, migrate code and data in steps, then remove; backfill in batches.
