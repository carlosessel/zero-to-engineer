By the end of this chapter you will understand what a container really is (an ordinary Linux process with isolation and limits, not a small virtual machine), how images are built from layers and cached, how to write Dockerfiles that are small, fast to rebuild and secure, how to run several services together with Docker Compose, and the mistakes that make containers slow, huge or dangerous. Containers are how almost all back-end software is now packaged and shipped, from a laptop to Kubernetes (<Ref to="m-kubernetes" />).

## What a container is

A **container** is a process (or group of processes) running on a shared Linux kernel, with two kernel features applied:

- **Namespaces** give it its own *view* of the system: its own process tree (it sees itself as PID 1), its own network interfaces and ports, its own file system root, hostname and users. It cannot see other containers' processes or files.
- **Control groups** (cgroups) *limit* what it can use: CPU, memory, number of processes, disk I/O. A container that exceeds its memory limit is killed by the out-of-memory killer (exit status 137, <Ref to="m-linux" />).

Its files come from an **image**: a packaged file system holding the application and everything it needs (runtime, libraries, configuration defaults). So the same image runs the same way on a developer's laptop, in CI and in production: the "works on my machine" problem largely disappears.

Compared with a **virtual machine**, which emulates hardware and runs its own operating system kernel, a container shares the host's kernel. Containers start in milliseconds, use far less memory, and pack densely; virtual machines isolate more strongly, which is why cloud providers run containers *inside* VMs for different customers. On macOS and Windows, Docker Desktop runs a small Linux VM to host the containers.

The ecosystem follows the **OCI** (Open Container Initiative) standards for images and runtimes, so images built with Docker run under containerd, Podman, CRI-O and Kubernetes alike.

## Images and layers

An image is a stack of read-only **layers**, each the file-system changes made by one instruction of a **Dockerfile**, plus metadata (the default command, environment variables, exposed ports). A running container adds a thin writable layer on top, which disappears with the container: **containers are disposable**, and anything that must last goes in a **volume** or an external service (<Ref to="m-cloud-patterns" />).

Layers are shared and cached. Images built on the same base share its layers on disk and in transfers, and when you rebuild, Docker reuses every layer whose instruction and inputs have not changed, **up to the first one that has**; everything after it is rebuilt. That makes the **order of instructions** the key to fast builds:

```ts
type Step = { instruction: string; inputs: string[] };

function rebuilt(steps: Step[], changed: Set<string>): string[] {
  let cacheBroken = false;
  return steps.map((s) => {
    if (!cacheBroken && s.inputs.some((i) => changed.has(i))) cacheBroken = true;
    return `${cacheBroken ? "REBUILD" : "cached "} ${s.instruction}`;
  });
}

const naive: Step[] = [
  { instruction: "FROM node:24-slim", inputs: [] },
  { instruction: "COPY . .", inputs: ["src/server.ts", "package.json", "package-lock.json"] },
  { instruction: "RUN npm ci", inputs: [] },
  { instruction: "RUN npm run build", inputs: [] },
];

const ordered: Step[] = [
  { instruction: "FROM node:24-slim", inputs: [] },
  { instruction: "COPY package.json package-lock.json ./", inputs: ["package.json", "package-lock.json"] },
  { instruction: "RUN npm ci", inputs: [] },
  { instruction: "COPY . .", inputs: ["src/server.ts"] },
  { instruction: "RUN npm run build", inputs: [] },
];

const codeChange = new Set(["src/server.ts"]);
console.log(rebuilt(naive, codeChange));
console.log(rebuilt(ordered, codeChange));
```

It prints the naive Dockerfile rebuilding `COPY . .`, `RUN npm ci` and the build after a one-line code change, while the ordered one shows `cached` for the dependency steps and rebuilds only from `COPY . .` onwards. Installing dependencies can take minutes; copying the dependency files first means it happens only when they change. The same applies to Maven (`COPY pom.xml` then `mvn dependency:go-offline`) and .NET (`COPY *.csproj` then `dotnet restore`).

## A good Dockerfile

A production Dockerfile for a Node.js service, using a **multi-stage build**:

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build && npm prune --omit=dev

FROM node:24-slim AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
USER node
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s CMD node dist/healthcheck.js
CMD ["node", "dist/server.js"]
```

What each choice does:

- **Multi-stage**: the `build` stage has compilers and development dependencies; the final `runtime` stage copies in only the built output and production dependencies, so the shipped image is smaller and has less in it for attackers to use.
- **Small, specific base images**: `-slim` variants (or Alpine, or **distroless** images with no shell or package manager at all) and a **pinned version** (`node:24-slim`, ideally pinned by digest), never `latest`, so builds are repeatable.
- **Dependencies before code**, for layer caching.
- **`USER node`**: do not run as root inside the container (<Ref to="m-linux" />). If the application is compromised, the attacker is an unprivileged user.
- **Exec-form `CMD ["node", "dist/server.js"]`**: the application runs as PID 1 and receives SIGTERM directly. With the shell form (`CMD node dist/server.js`), a shell is PID 1 and may not forward signals, so `docker stop` waits and then SIGKILLs the app, skipping graceful shutdown.
- A **`.dockerignore`** file (listing `node_modules`, `.git`, `.env`, test data) keeps the build context small and stops secrets and local junk being copied in.

Java and .NET follow the same shape: build with the SDK image (`maven:3-eclipse-temurin-25` or `mcr.microsoft.com/dotnet/sdk:10.0`), run with a JRE-only or ASP.NET runtime image (`eclipse-temurin:25-jre`, `mcr.microsoft.com/dotnet/aspnet:10.0`, or their distroless and "chiseled" variants). Java and .NET both read container memory limits from cgroups and size their heaps accordingly (<Ref to="m-memory-gc" />).

**Never put secrets in an image.** Anything copied in or set with `ENV` or `ARG` is readable by anyone who can pull the image, even if a later layer deletes it (earlier layers still contain it). Pass secrets at run time from the platform (<Ref to="m-cloud-patterns" />), and use BuildKit secret mounts (`RUN --mount=type=secret,...`) for credentials needed during the build.

## Running containers

The everyday commands:

```bash
docker build -t orders-api:1.4.2 .
docker run -d --name orders -p 8080:8080 \
  --memory 512m --cpus 1 \
  -e DATABASE_URL=postgres://db/orders \
  orders-api:1.4.2
docker ps
docker logs -f orders
docker exec -it orders sh
docker stop orders
```

`-p 8080:8080` publishes the container's port on the host; `--memory` and `--cpus` set cgroup limits; `-e` passes configuration; `docker logs` reads what the process wrote to standard output (<Ref to="m-cloud-patterns" />); `docker exec` opens a shell inside for debugging (not possible in distroless images, which is part of their point); `docker stop` sends SIGTERM, then SIGKILL after 10 seconds by default.

**Tag images** with something immutable and traceable (a version or the Git commit hash), push them to a **registry** (Docker Hub, GitHub Container Registry, Amazon ECR, Azure Container Registry), and deploy by tag or digest. Rebuilding "the same" tag later can produce a different image; deploying by digest guarantees the exact bytes.

## Docker Compose

**Docker Compose** describes several containers that work together, with their networks and volumes, in one file. It is ideal for local development and integration testing: one command starts the API, its database, a cache and a message broker.

```yaml
services:
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      DATABASE_URL: postgres://orders:dev-only-password@db:5432/orders
      REDIS_URL: redis://cache:6379
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started

  db:
    image: postgres:17
    environment:
      POSTGRES_USER: orders
      POSTGRES_PASSWORD: dev-only-password
      POSTGRES_DB: orders
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U orders"]
      interval: 5s
      retries: 10

  cache:
    image: redis:8

volumes:
  db-data:
```

`docker compose up` builds the API and starts all three. Services find each other **by name** on a private network Compose creates (`db:5432`, `cache:6379`); `depends_on` with a health condition waits until PostgreSQL actually accepts connections, not just until its container has started; the **named volume** `db-data` keeps the database's files when containers are recreated. The password here is for a local throwaway database only; real environments get secrets from a secrets manager.

## Security and size

- **Scan images** for known vulnerabilities in their packages (Trivy, Grype, Docker Scout, registry scanners) in CI, and rebuild regularly to pick up base-image patches.
- **Minimal images**: fewer packages, fewer vulnerabilities, smaller downloads, faster starts.
- **Non-root users**, a **read-only root file system** where possible (`--read-only`, with a writable `/tmp` if needed), and dropped Linux capabilities.
- **Never mount the Docker socket** into a container unless you understand it gives full control of the host.
- **Sign images** and verify signatures on deployment (Sigstore's cosign) to defend the supply chain (covered in the security part of this course).

## Common mistakes

- **`COPY . .` before installing dependencies**, rebuilding everything on every change.
- **`latest` tags** and unpinned base images.
- **Running as root.**
- **Shell-form `CMD`**, so the app never receives SIGTERM.
- **Secrets in images**, build arguments or layers "deleted" later.
- **Storing data in the container's writable layer**, lost when it is replaced.
- **One container running several unrelated processes** (the API, a cron daemon and a database) instead of one concern per container.
- **No memory limits**, so one container can starve the host; or limits lower than the runtime's heap settings.

## Practice

**1. (warm-up)** What two Linux kernel features make a container, and what does each provide?

<Solution>

Namespaces, which give the process its own view of processes, network, file system, hostname and users; and control groups (cgroups), which limit how much CPU, memory, I/O and how many processes it can use.

</Solution>

**2. (warm-up)** Why does `CMD ["node", "server.js"]` handle `docker stop` better than `CMD node server.js`?

<Solution>

The exec form runs Node directly as PID 1, so it receives the SIGTERM that `docker stop` sends and can shut down gracefully. The shell form runs `/bin/sh -c "node server.js"`; the shell is PID 1 and may not forward the signal, so Node never hears it, and Docker kills it with SIGKILL after the timeout.

</Solution>

**3. (standard)** Use the layer simulation to show which steps rebuild when only `package-lock.json` changes, for both Dockerfiles.

<Solution>

```ts
type Step = { instruction: string; inputs: string[] };

function rebuilt(steps: Step[], changed: Set<string>): string[] {
  let cacheBroken = false;
  return steps.map((s) => {
    if (!cacheBroken && s.inputs.some((i) => changed.has(i))) cacheBroken = true;
    return `${cacheBroken ? "REBUILD" : "cached "} ${s.instruction}`;
  });
}

const ordered: Step[] = [
  { instruction: "FROM node:24-slim", inputs: [] },
  { instruction: "COPY package.json package-lock.json ./", inputs: ["package.json", "package-lock.json"] },
  { instruction: "RUN npm ci", inputs: [] },
  { instruction: "COPY . .", inputs: ["src/server.ts"] },
  { instruction: "RUN npm run build", inputs: [] },
];

console.log(rebuilt(ordered, new Set(["package-lock.json"])));
```

It prints everything from `COPY package.json package-lock.json ./` onwards as **REBUILD**: a dependency change must reinstall dependencies and rebuild, which is correct. Only the base image stays cached. The naive Dockerfile rebuilds the same steps here; the difference is that it also rebuilds dependencies for every code change.

</Solution>

**4. (standard)** A teammate's image is 1.4 GB and contains the TypeScript compiler, test files and a `.env` file. List the fixes.

<Solution>

Use a multi-stage build so the final stage contains only production dependencies and built output (no compiler or tests); use a slim or distroless runtime base image; add a `.dockerignore` excluding `.env`, `.git`, tests and `node_modules`; remove the secret from the image entirely, rotate it because it has been exposed to anyone with the image, and inject it at run time; then scan the new image for vulnerabilities.

</Solution>

**5. (stretch)** Your Compose setup starts the API before PostgreSQL is ready, so the API crashes on start. Give two fixes, and say which is better for production.

<Solution>

In Compose, add a health check to the database and `depends_on` with `condition: service_healthy`, so the API starts only once PostgreSQL accepts connections. Independently, make the API itself tolerate an unavailable database at start-up: retry the connection with backoff and report "not ready" until it succeeds. The second is what matters in production, where no orchestrator guarantees start order and databases restart or fail over at any time (<Ref to="m-resilience" />).

</Solution>

## Summary

- A **container** is a Linux process isolated by **namespaces** and limited by **cgroups**, sharing the host kernel; lighter than a virtual machine, with weaker isolation.
- **Images** are stacks of cached, shared **layers**; containers are disposable, with lasting data in **volumes** or external services.
- Order Dockerfiles for caching (**dependencies before code**); use **multi-stage builds**, small pinned base images, a non-root **user**, exec-form `CMD`, and `.dockerignore`.
- Never put **secrets** in images; inject them at run time.
- Tag images immutably, push to a **registry**, deploy by tag or digest; set memory and CPU limits.
- **Docker Compose** runs multi-container setups for development and tests, with service names, health-gated dependencies and named volumes.
- Scan, minimise, sign and harden images.
