By the end of this chapter you will store and query data from a Spring Boot service with **Spring Data JPA**: entities mapped to tables, repositories whose queries are generated from method names, JPQL queries and projections, schema changes with **Flyway** migrations, transactions with `@Transactional`, optimistic locking, and the lazy-loading traps (N+1 queries and `LazyInitializationException`) that catch every JPA newcomer. <Ref to="sql" />, <Ref to="m-relational" /> and <Ref to="m-schema-design" /> cover the database side; this chapter is how a Spring service talks to it.

## JPA, Hibernate and Spring Data

Three layers work together:

- **JPA** (Jakarta Persistence) is the standard Java API for mapping objects to tables: annotations such as `@Entity` and `@Id`, and the `EntityManager` that loads and saves entities.
- **Hibernate** is the ORM that implements JPA: it generates the SQL, tracks changes and caches entities within a transaction.
- **Spring Data JPA** adds **repositories**: you declare an interface, and Spring writes the implementation, including queries derived from method names.

This chapter builds one small project. In production you would use **PostgreSQL** (with the `org.postgresql:postgresql` driver); the examples use **H2**, an in-memory database that runs inside the application in PostgreSQL compatibility mode, so they need nothing installed. The build file:

```kotlin
plugins {
    java
    id("org.springframework.boot") version "4.1.2"
    id("io.spring.dependency-management") version "1.1.7"
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-data-jpa")
    implementation("org.springframework.boot:spring-boot-starter-flyway")
    runtimeOnly("com.h2database:h2")
}
```

The starters bring Hibernate, Spring Data JPA, a connection pool (HikariCP) and Flyway.

## Migrations first

With JPA it is tempting to let Hibernate create tables from your classes (`ddl-auto=update`). Don't, outside throwaway experiments: it cannot rename or move data, it never removes anything, and nobody reviews what it does to production. Instead, write the schema as versioned SQL **migrations** that **Flyway** applies in order at start-up (or in your deployment pipeline), and let Hibernate only **validate** that the classes match. The first migration, `src/main/resources/db/migration/V1__create_customers_and_orders.sql`:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(254) NOT NULL UNIQUE
);

CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers (id),
    total_pence INT NOT NULL CHECK (total_pence >= 0),
    status VARCHAR(20) NOT NULL,
    version INT NOT NULL DEFAULT 0
);

CREATE INDEX ix_orders_customer_id ON orders (customer_id);
```

Flyway records each applied migration in a `flyway_schema_history` table, runs only the new ones, and refuses to start if an applied migration was edited. To change the schema, add `V2__add_order_note.sql` and so on; never edit one that has already run anywhere. Design changes that the version still running can live with: add a nullable column, deploy, backfill, then add the constraint in a later migration (<Ref to="m-delivery" />).

The settings, in `src/main/resources/application.properties`:

```properties
spring.datasource.url=jdbc:h2:mem:bakery;MODE=PostgreSQL
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
spring.jpa.properties.hibernate.generate_statistics=true
spring.main.banner-mode=off
logging.level.root=warn
logging.level.org.hibernate.engine.internal.StatisticalLoggingSessionEventListener=off
```

- The **datasource URL** says which database to use. In production it, the user and the password come from environment variables (`SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_PASSWORD`), never from committed files.
- **`ddl-auto=validate`**: Hibernate checks the tables match the entities and refuses to start if not.
- **`open-in-view=false`**: by default Spring keeps the database session open while a web response is written, which hides lazy-loading problems and holds connections longer than needed. Turn it off.
- Statistics are switched on here only so the example can count queries; the last lines quieten the logs.

## Entities

An **entity** is a class mapped to a table. `Customer.java`:

```java
package com.bakery;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    private String email;

    @OneToMany(mappedBy = "customer")
    private List<CustomerOrder> orders = new ArrayList<>();

    protected Customer() {}

    public Customer(String name, String email) {
        this.name = name;
        this.email = email;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public String getEmail() { return email; }
    public List<CustomerOrder> getOrders() { return orders; }
}
```

and `CustomerOrder.java` (named so because `ORDER` is a reserved word in SQL):

```java
package com.bakery;

import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;
import jakarta.persistence.Version;

@Entity
@Table(name = "orders")
public class CustomerOrder {
    public enum Status { PLACED, PAID, DELIVERED, CANCELLED }

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id")
    private Customer customer;

    private int totalPence;

    @Enumerated(EnumType.STRING)
    private Status status;

    @Version
    private int version;

    protected CustomerOrder() {}

    public CustomerOrder(Customer customer, int totalPence) {
        this.customer = customer;
        this.totalPence = totalPence;
        this.status = Status.PLACED;
    }

    public Long getId() { return id; }
    public Customer getCustomer() { return customer; }
    public int getTotalPence() { return totalPence; }
    public Status getStatus() { return status; }

    public void cancel() {
        if (status == Status.DELIVERED) throw new IllegalStateException("Order " + id + " was already delivered");
        status = Status.CANCELLED;
    }
}
```

- **`@Entity`** and **`@Table`** map the class to a table; **`@Id`** with `GenerationType.IDENTITY` uses the database's generated keys. Column names are derived from field names (`totalPence` becomes `total_pence`).
- **`@ManyToOne`** maps the foreign key `customer_id` to a `Customer`; **`@OneToMany(mappedBy = "customer")`** is the other side. Use **`FetchType.LAZY`** for `@ManyToOne` (the default is eager, which loads the customer with every order whether you need it or not); `@OneToMany` is lazy by default.
- **`@Enumerated(EnumType.STRING)`** stores the enum's name; the default stores its position, which breaks silently if someone reorders the values.
- **`@Version`** turns on optimistic locking, shown below.
- JPA needs a no-argument constructor; making it `protected` keeps other code using the real one. Behaviour such as `cancel()` lives on the entity, which protects its own rules (<Ref to="m-ddd" />).

## Repositories

A **repository** is an interface; Spring Data implements it at start-up. `Repositories.java`:

```java
package com.bakery;

import java.util.List;
import java.util.Optional;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;

record CustomerTotal(String customer, long orders, long totalPence) {}

interface CustomerRepository extends JpaRepository<Customer, Long> {
    Optional<Customer> findByEmail(String email);

    @EntityGraph(attributePaths = "orders")
    List<Customer> findAllByOrderByNameAsc();
}

interface OrderRepository extends JpaRepository<CustomerOrder, Long> {
    List<CustomerOrder> findByStatusAndTotalPenceGreaterThanOrderByTotalPenceDesc(CustomerOrder.Status status, int totalPence);

    Page<CustomerOrder> findByStatus(CustomerOrder.Status status, Pageable pageable);

    @Query("""
        select new com.bakery.CustomerTotal(o.customer.name, count(o), sum(o.totalPence))
        from CustomerOrder o
        where o.status <> com.bakery.CustomerOrder.Status.CANCELLED
        group by o.customer.name
        order by o.customer.name
        """)
    List<CustomerTotal> totalsByCustomer();
}
```

- **`JpaRepository<Customer, Long>`** gives you `save`, `findById`, `findAll`, `deleteById`, `count` and more, for free.
- **Derived queries**: Spring parses method names such as `findByEmail` or `findByStatusAndTotalPenceGreaterThanOrderByTotalPenceDesc` and generates the query. Keep them short; when a name gets as long as that one, prefer `@Query`.
- **`Pageable`** adds paging and sorting; a **`Page`** also carries the total count.
- **`@Query`** takes **JPQL**, a SQL-like language over entities and their fields rather than tables and columns. `select new ...` builds a record directly: a **projection**, which loads only what you need.
- **`@EntityGraph(attributePaths = "orders")`** loads the customers' orders in the same query.

## Services and transactions

Business operations belong in services, and each should run in one **transaction**. **`@Transactional`** on a public method of a Spring bean starts a transaction before the method and commits it after, or rolls it back if an unchecked exception escapes. `OrderService.java`:

```java
package com.bakery;

import java.util.NoSuchElementException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {
    private final OrderRepository orders;

    public OrderService(OrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public CustomerOrder cancel(long id) {
        CustomerOrder order = orders.findById(id).orElseThrow(() -> new NoSuchElementException("No order " + id));
        order.cancel();
        return order;
    }

    @Transactional(readOnly = true)
    public CustomerOrder.Status statusOf(long id) {
        return orders.findById(id).map(CustomerOrder::getStatus).orElseThrow();
    }
}
```

Notice that `cancel` never calls `save`: entities loaded inside a transaction are **managed**, and Hibernate writes their changes when the transaction commits (**dirty checking**). `readOnly = true` lets Hibernate skip that work for queries. `@Transactional` works through a proxy, so it has no effect on calls from one method to another inside the same class, or on private methods.

## Seeing it work

The demo in `BakeryApplication.java` uses everything above, counting SQL statements with Hibernate's statistics:

```java
package com.bakery;

import jakarta.persistence.EntityManagerFactory;
import org.hibernate.SessionFactory;
import org.hibernate.stat.Statistics;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Sort;
import org.springframework.transaction.support.TransactionTemplate;

@SpringBootApplication
public class BakeryApplication {
    public static void main(String[] args) {
        SpringApplication.run(BakeryApplication.class, args).close();
    }

    @Bean
    CommandLineRunner demo(CustomerRepository customers, OrderRepository orders, OrderService service, TransactionTemplate tx, EntityManagerFactory emf) {
        return args -> {
            Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
            var ama = customers.save(new Customer("Ama", "ama@example.com"));
            var kofi = customers.save(new Customer("Kofi", "kofi@example.com"));
            orders.save(new CustomerOrder(ama, 1250));
            orders.save(new CustomerOrder(ama, 3100));
            orders.save(new CustomerOrder(kofi, 450));
            System.out.println(customers.findByEmail("kofi@example.com").map(Customer::getName).orElse("none"));
            for (var o : orders.findByStatusAndTotalPenceGreaterThanOrderByTotalPenceDesc(CustomerOrder.Status.PLACED, 1000)) {
                System.out.println(o.getId() + " " + o.getTotalPence());
            }
            var page = orders.findByStatus(CustomerOrder.Status.PLACED, PageRequest.of(0, 2, Sort.by("id")));
            System.out.println(page.getNumberOfElements() + " of " + page.getTotalElements() + " in " + page.getTotalPages() + " pages");
            orders.totalsByCustomer().forEach(System.out::println);

            stats.clear();
            tx.executeWithoutResult(s -> {
                long sum = 0;
                for (var c : customers.findAll()) sum += c.getOrders().stream().mapToInt(CustomerOrder::getTotalPence).sum();
                System.out.println("lazy loop: " + stats.getPrepareStatementCount() + " queries, total " + sum);
            });
            stats.clear();
            long sum = customers.findAllByOrderByNameAsc().stream().flatMap(c -> c.getOrders().stream()).mapToInt(CustomerOrder::getTotalPence).sum();
            System.out.println("entity graph: " + stats.getPrepareStatementCount() + " query, total " + sum);

            try {
                customers.findById(ama.getId()).orElseThrow().getOrders().size();
            } catch (org.hibernate.LazyInitializationException e) {
                System.out.println("outside a transaction: LazyInitializationException");
            }

            long firstId = orders.findAll(Sort.by("id")).get(0).getId();
            CustomerOrder stale = orders.findById(firstId).orElseThrow();
            service.cancel(firstId);
            System.out.println("cancelled: " + service.statusOf(firstId));
            try {
                stale.cancel();
                orders.save(stale);
            } catch (org.springframework.orm.ObjectOptimisticLockingFailureException e) {
                System.out.println("stale copy refused: someone changed order " + firstId + " first");
            }
        };
    }
}
```

Run it with:

```bash
./gradlew bootRun
```

Besides a warning or two from the libraries, it prints:

```text
Kofi
2 3100
1 1250
2 of 3 in 2 pages
CustomerTotal[customer=Ama, orders=2, totalPence=4350]
CustomerTotal[customer=Kofi, orders=1, totalPence=450]
lazy loop: 3 queries, total 4800
entity graph: 1 query, total 4800
outside a transaction: LazyInitializationException
cancelled: CANCELLED
stale copy refused: someone changed order 1 first
```

Line by line:

- The derived queries found Kofi by email, and the two placed orders over £10, largest first.
- The page holds 2 of the 3 placed orders, in 2 pages.
- The JPQL projection grouped and summed in the database.
- **The N+1 problem**: looping over customers and touching each one's lazy `orders` list ran one query for the customers plus one per customer. With two customers that is 3; with 2,000 it is 2,001 (<Ref to="m-performance" />). The entity graph loaded everything in one query. A `join fetch` in JPQL does the same.
- **`LazyInitializationException`**: `findById` ran in its own short transaction, which had ended, so the lazy `orders` list could no longer be loaded. Load what you need inside the service's transaction, with an entity graph, `join fetch` or a projection, and return DTOs rather than entities.
- **Optimistic locking**: `stale` was loaded before the service cancelled the order. Saving it ran `UPDATE ... WHERE id = 1 AND version = 0`, which matched no row because the version was now 1, so Spring threw `ObjectOptimisticLockingFailureException` instead of silently overwriting the change. An API turns this into **409 Conflict** (<Ref to="be-http" />).

## In a web service

Controllers call services, never repositories directly for anything beyond trivial reads, and return DTO records, not entities (which would expose every field, trigger lazy loading during JSON writing, and tie your API to your tables):

```java
@GetMapping("/orders/{id}")
ResponseEntity<OrderDto> get(@PathVariable long id) {
    return ResponseEntity.of(orders.findById(id).map(o -> new OrderDto(o.getId(), o.getTotalPence(), o.getStatus().name())));
}
```

For queries you write yourself with `@Query(nativeQuery = true)` or `JdbcClient`, always use **parameters** (`:email` or `?`), never string concatenation, so input can never change the SQL (<Ref to="m-appsec" />).

## Common mistakes

- **`ddl-auto=update` or `create`** against real databases instead of migrations.
- **Editing a migration** that has already run somewhere.
- **N+1 queries** from loops over lazy relationships.
- **Eager fetching everywhere** to avoid lazy-loading errors, which loads half the database on every query.
- **Returning entities from controllers**, or leaving `open-in-view` on to hide the resulting errors.
- **`@Transactional` on private methods** or self-calls, where it does nothing.
- **`EnumType.ORDINAL`** (the default) for enums.

## Practice

**1. (warm-up)** What query does Spring Data derive from `List<Customer> findByNameStartingWithOrderByNameAsc(String prefix)`?

<Solution>

Roughly `select c from Customer c where c.name like :prefix% order by c.name asc`: customers whose name starts with the given text, sorted by name. Spring adds the `%` and escapes the value, so it is a safe parameter.

</Solution>

**2. (warm-up)** Why does the example set `ddl-auto=validate` and use Flyway, rather than letting Hibernate create the tables?

<Solution>

Migrations are reviewed, versioned SQL that run the same way in every environment and can rename columns or move data; Hibernate's automatic schema updates can do neither, never remove anything, and change production without anyone reviewing it. `validate` keeps the safety net: the application refuses to start if the entities and the tables disagree.

</Solution>

**3. (standard)** Write the next migration: add an optional `note` column (up to 500 characters) to `orders`, and an index on `status`. What is its file name?

<Solution>

`src/main/resources/db/migration/V2__add_order_note_and_status_index.sql`:

```sql
ALTER TABLE orders ADD COLUMN note VARCHAR(500);

CREATE INDEX ix_orders_status ON orders (status);
```

Then add `private String note;` (with a getter) to `CustomerOrder`, so `validate` passes. The column is nullable, so the version of the service still running, which does not know about it, keeps working.

</Solution>

**4. (stretch)** An endpoint lists 50 orders with each customer's name, and is slow. The logs show 51 SQL statements per request. Explain why, and give two ways to fix it.

<Solution>

The query loads 50 orders; each order's `customer` is lazy, so reading `order.getCustomer().getName()` for each one runs another query: 1 + 50, the N+1 problem. Fixes: add `join fetch o.customer` to the JPQL (or `@EntityGraph(attributePaths = "customer")` on the repository method), so one query loads both; or, better for a read-only list, a projection query (`select new com.bakery.OrderRow(o.id, o.customer.name, o.totalPence) from CustomerOrder o ...`) that selects just the three columns with one join.

</Solution>

## Summary

- **JPA** is the standard, **Hibernate** implements it, **Spring Data JPA** generates **repositories**.
- Manage the schema with **Flyway migrations** (`V1__...sql`), never edit applied ones, and set `ddl-auto=validate`.
- **Entities**: `@Entity`, `@Id`, `@ManyToOne(fetch = LAZY)`, `@OneToMany(mappedBy)`, `@Enumerated(STRING)`, `@Version`.
- Queries: **derived queries** from method names, **JPQL** with `@Query`, **projections** into records, **paging** with `Pageable`.
- **`@Transactional`** services; managed entities are saved by **dirty checking**.
- Beware **N+1** (fix with entity graphs, `join fetch` or projections) and **`LazyInitializationException`** (load what you need inside the transaction; turn off `open-in-view`); **optimistic locking** turns lost updates into errors you can report as 409.
