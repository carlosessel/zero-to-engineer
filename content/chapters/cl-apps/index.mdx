By the end of this chapter you will know the features of the Claude apps that turn single chats into a working environment: projects that hold your context, memory you control, artifacts you can share, connections to your other tools, and skills that make a good workflow repeatable. Most people use a fraction of these; using them well saves you from re-explaining yourself every day.

The apps are claude.ai in a browser, the desktop app for macOS and Windows, and the phone apps. Features and plan details here come from Anthropic's help centre, checked in **November 2026**. Menus move and features roll out in stages, so if something is not where this chapter says, search the [help centre](https://support.claude.com/).

## The everyday basics

A few habits make every chat better:

- **One task per conversation.** Start a new chat when you change subject. The whole conversation is reread for every reply (<Ref to="cl-how-it-works" />), so an old, unrelated discussion only gets in the way.
- **Attach the real thing.** Drag in the file, the screenshot, the PDF, the spreadsheet, rather than describing it. Claude reads images and documents directly.
- **Edit your message instead of arguing.** If a reply went wrong because your request was unclear, edit the original message and send it again, rather than adding corrections underneath. The conversation stays clean.
- **Choose the model and effort** for the task (<Ref to="cl-models" />).

## Projects: context that persists

A **project** is a workspace with its own chats, its own **instructions** and its own **knowledge**: files you add once, which every chat in the project can use. Projects are available on every plan; free accounts can have up to five.

Use a project for anything you return to: a course you are studying, a codebase you are learning, a piece of writing, a job search. Set it up once:

1. **Instructions**: what this project is, who you are in it, and how you want answers. This works like a system prompt (<Ref to="cl-prompting" />) for every chat in the project.
2. **Knowledge**: the documents Claude should know: the syllabus, the style guide, the specification, your notes.

For example, a project for studying this course might have these instructions:

```text
I am working through a course to become a strong software engineer. I know
Python and some TypeScript; I am new to Java and C#. When I ask about a
concept, explain it in plain words first, then show a short example in
TypeScript, then Java if the languages differ. When I paste my answer to an
exercise, do not give me the solution: point out the first mistake and ask
me a question that leads me to it.
```

When a project's knowledge grows large, paid plans switch to retrieval: rather than putting every file into the context at once, Claude finds and reads the relevant parts (the help centre says this expands capacity by up to ten times). This technique is called retrieval-augmented generation, and <Ref to="rag" /> in the AI course explains how it works.

(Anthropic was rolling out a new version of projects in stages when this was checked, starting with some Claude Code users; the ideas are the same.)

## Memory: what Claude keeps about you

Outside projects, the apps can build a **memory** of you across conversations: your role, your projects, your preferences, ongoing work. It is saved as separate topics while you chat, and the app adds relevant ones to new conversations. This is not the model remembering (it still starts each reply fresh); it is the app putting saved notes into the context.

You stay in control:

- **See and edit it** in Settings, under **Your Claude**, then **Manage** next to **Your memory**. Read every topic, change it, or delete it.
- **Pause or reset it** with the **Generate memory from chats** switch.
- **Incognito chats** (the ghost icon) are not saved to your history or memory.
- **Each project has its own memory**, and does not see other projects' memory. A project can also be cut off from your account-wide memory.

The help centre says some sensitive information (for example government ID numbers and financial account numbers) is never saved, and sensitive topics such as health are left out unless you opt in. Even so, a good habit: look at your memory now and then, and correct anything wrong. A wrong remembered "fact" quietly affects every later conversation.

## Artifacts: work you can keep and share

An **artifact** is something Claude makes that you would put in front of someone: a document, a slide deck, a design, a data analysis, a diagram, a small website or interactive tool. It opens in a panel beside the chat, where you can view it, edit it, keep improving it, and come back to it later.

Ask for one directly: "Make a one-page explainer of how our caching works, with a diagram" or "Build a small interactive quiz on these ten terms". When checked, the kinds included **Docs**, **Slides** and **Design** on every plan, plus **Data** on paid plans and several in beta.

What makes artifacts more than files:

- **They start private** to you, and you choose whether to share them.
- **They can be exported**: documents and slides to formats such as Word, PowerPoint and PDF.
- **They can be small apps.** An interactive artifact can call Claude itself, with each person's use counting against their own plan, so you can build a study tool or a team helper with no server and no API key. On paid plans artifacts can also store data between visits; the help centre advises checking whether an artifact uses shared storage before typing anything sensitive into it.

An artifact is a fast way to make a learning aid for yourself: flashcards from your notes, an interactive diagram of an algorithm, a quiz on a chapter.

## Files, code and analysis

When **code execution and file creation** is turned on (in Settings, under **Capabilities**), Claude can run code in a sandbox to analyse data, make charts, and create files such as spreadsheets, documents and presentations. Upload a CSV and ask "Which product's sales fell most last month? Show a chart." Claude writes and runs the analysis code, so the numbers come from computation rather than recollection. Ask to see the code when it matters; it is a check you can read.

## Connectors: your other tools

**Connectors** let Claude reach your other apps and services: search your documents in a drive, read and create issues in a tracker, look at a calendar, send a message. You add them in **Customize**, then **Connectors**, and sign in to each service.

Under the hood, many connectors use the **Model Context Protocol (MCP)**, an open standard for connecting AI applications to tools and data. You can also add a **custom connector** that points at any remote MCP server (free accounts can have one). The Claude Code part of this course explains MCP properly.

Two cautions from the help centre, which matter more than they look:

- **Connect only services you trust and need.** Each connector gives Claude access to that service's data, and often the power to act in it.
- **Custom connectors reach services Anthropic has not checked.** Review what access you grant.

A connector to your email, for instance, means text written by strangers (the emails) enters Claude's context. That text could contain instructions designed to manipulate it, a **prompt injection**. Be most careful with connectors that can both read untrusted content and take actions.

## Skills and plugins: repeatable expertise

A **skill** is a folder of instructions (and optionally scripts and other files) that teaches Claude a specific workflow: your company's report format, how your team reviews a contract, a checklist for a data clean-up. Claude reads a short description of each skill and loads the full instructions only when a task calls for it, so you can have many without filling the context.

- **Built-in skills** from Anthropic handle Excel, Word, PowerPoint and PDF work, and Claude uses them automatically.
- **Custom skills** you write yourself: a folder containing a `SKILL.md` file (the instructions, with a name and description at the top), zipped and uploaded under **Customize**, then **Skills**. Skills need code execution turned on.

The same skill format works in Claude Code and the API, which is what makes skills powerful: write a workflow once and use it everywhere. The Claude Code part of this course shows how to write good ones.

A **plugin** bundles skills and other extensions so they can be installed together and shared, for example across a team.

## Research

For questions that need many sources, the apps have a **research** mode that searches widely, reads, and writes a report with citations. It takes longer than a normal reply. Use it for a landscape ("What are the main approaches to rate limiting in distributed systems, and who uses which?"), not for a quick fact. And check the citations, as always: a cited source can still be misread.

## Choosing where to work

| You want to… | Use |
|---|---|
| Think through a problem, learn a topic, draft writing | A chat, in a project if you will come back to it |
| Study a course or codebase over weeks | A project with instructions and the key documents |
| Make something to share: a document, deck, diagram or small tool | An artifact |
| Analyse a spreadsheet or make a chart | A chat with code execution turned on |
| Work with your documents, tickets or calendar | Connectors |
| Repeat the same workflow often, the same way | A skill |
| Change code in a project, run tests, make commits | Claude Code (the next part of this course) |

## Common mistakes

- **Re-explaining your context in every chat** instead of putting it in a project's instructions and knowledge.
- **Never checking memory**, so an outdated or wrong "fact" about you shapes later answers.
- **Long chats on many subjects.** Start a new chat per task.
- **Connecting everything "just in case".** Each connector is access; connect what you need.
- **Trusting numbers from a chat without code execution.** For data, let Claude compute, and look at the code.
- **Typing sensitive data into a shared artifact** without checking where it is stored.

## Practice

**1. (warm-up)** What is the difference between a project's instructions and its knowledge?

<Solution>

Instructions say how Claude should behave in every chat of the project: who you are, what the project is, how to answer. Knowledge is the material it should know: files and documents it can read and search when answering.

</Solution>

**2. (warm-up)** Claude keeps assuming you work in Java, though you switched to C# months ago. Where do you fix this?

<Solution>

In its memory: Settings, **Your Claude**, **Manage** next to **Your memory**. Edit or delete the outdated topic. (If it only happens in one project, check that project's memory and instructions.)

</Solution>

**3. (standard)** Write project instructions for preparing for software engineering interviews, so that Claude acts as an interviewer and coach rather than giving away answers.

<Solution>

For example:

```text
I am preparing for junior back-end engineering interviews (Java or C#).
Act as an interviewer. When I ask for practice, give me one problem at a
time, at the level of a real interview, and wait for my answer. Do not
show solutions unless I type "show me". When I answer, first say what was
good, then the most important problem, as a hint or question. For design
questions, ask the follow-up questions a real interviewer would. Keep a
running list, at the end of each answer, of topics I should review.
```

</Solution>

**4. (standard)** You want a connector to your email so Claude can draft replies. What risk should you consider, and what would reduce it?

<Solution>

Emails are written by other people, so their text enters Claude's context and could contain instructions meant to manipulate it (prompt injection), for example to forward information or send messages. Reduce the risk by connecting only what you need, preferring access that can read and draft but not send without your approval, reviewing actions before they happen, and being wary of combining untrusted content with powerful actions.

</Solution>

**5. (standard)** Which feature fits each case? (a) Turning this chapter's key terms into flashcards you can flip through. (b) A monthly report your team always writes in the same structure. (c) Finding which week had the most returns in a CSV of sales.

<Solution>

(a) An **artifact**: an interactive flashcard tool. (b) A **skill** that holds the report's structure and steps, so every report comes out the same way (shared with the team, perhaps as a plugin). (c) A chat with **code execution** on, so Claude computes the answer from the file and you can check the code.

</Solution>

**6. (stretch)** Explain why skills load only a short description until a task needs them, using what you know about the context window.

<Solution>

Everything in the context costs tokens and attention, and irrelevant material can make results worse (<Ref to="cl-how-it-works" />). If every skill's full instructions were always loaded, having many skills would fill the context and distract Claude. Loading only a one-line description of each, and the full instructions when a task matches, keeps the context small and relevant while still letting Claude know what it can do.

</Solution>

## Summary

- Start a new chat per task, attach the real material, edit your message rather than argue, and choose the model.
- **Projects** hold **instructions** (like a system prompt) and **knowledge** (files) for work you return to; large knowledge is searched rather than all loaded.
- **Memory** saves topics about you across chats; you can view, edit, pause and reset it, and use incognito chats. Check it now and then.
- **Artifacts** are documents, slides, designs and small apps you can keep, export and share; interactive ones can call Claude.
- **Code execution** lets Claude compute from your files rather than recall.
- **Connectors** (often built on **MCP**) reach your other tools. Connect only what you trust and need; beware **prompt injection** from untrusted content.
- **Skills** package repeatable workflows, loading full instructions only when needed; **plugins** bundle them to share. The same skills work in Claude Code and the API.
