Zero to Software Engineer

Zero to Software EngineerRead, play with the demos, do the exercises, pass the quiz.

A software engineer turns a problem into working software that other people can rely on, and keeps it working as things change. Writing code is the visible part. Most of the job is thinking clearly.

Coding is telling a computer what to do. Engineering adds everything that makes the result dependable: understanding what is really needed, choosing a simple design, testing, working with others on the same code, releasing safely, and fixing things when they break at night. Someone who can do all of that is valuable in any language, and that is what this course builds, from nothing.

The route

    You will write better code once the machine stops being a mystery. Here is the whole thing in one sitting.

    The parts

    • Processor (CPU): carries out simple instructions, such as add, compare and copy, billions of times a second.
    • Memory (RAM): fast working space that is wiped when the power goes off. A running program lives here.
    • Storage (disk): slower, permanent space for files.
    • Operating system: Windows, macOS or Linux. It shares the hardware between programs and manages files.
    • Network: how computers send data to each other.

    Everything is numbers

    Computers store only on and off, written 1 and 0. One of these is a bit; eight make a byte, which can hold 256 different values. Numbers, text, images and sound are all encoded as bytes. Text uses an agreed table: in the common UTF-8 encoding the letter A is the number 65. A kilobyte is about a thousand bytes, a megabyte a million, a gigabyte a billion.

    What a program is

    A program is a text file of instructions written in a programming language. The processor cannot read that text directly, so another program translates it. A compiler translates the whole file ahead of time into a fast machine-code file (C, Go, Rust). An interpreter reads and runs it line by line (Python, JavaScript), which is slower but quicker to work with.

    name = "Ama"
age = 20
print(name, "will be", age + 1, "next year")

    Python runs this top to bottom: store a text, store a number, calculate, show the result. Every program, however large, is built from steps this small.

    Errors are part of the work

    When code is wrong, the computer stops and prints an error message naming the line and the problem. This happens to everyone, all day. You cannot break your computer by writing bad code. Read the message, fix, run again.

    The layers you will hear about

    Front end: what the user sees, in a browser or app. Back end: code on a server that holds the rules and talks to the database. Database: where data is kept. Infrastructure: the machines and networks it all runs on. A “full-stack” engineer works across all of them.

    Programmers give the computer typed commands instead of clicking. It looks intimidating for about a day. You need fewer than ten commands.

    Files, folders and paths

    A file holds data: a photo, a document, a program. Its extension, the part after the dot, says what kind: .py is Python code, .txt is plain text, .csv is a table, .json is structured data. A folder (also called a directory) holds files and other folders. A path is the address of a file, such as Documents/ai-course/hello.py.

    As programs grow, loose variables and functions become hard to follow. Classes bundle related data and behaviour into one named thing.

    class BankAccount:
    def __init__(self, owner, balance=0):    # runs when an account is created
        self.owner = owner                   # data stored on this object
        self.balance = balance

    def deposit(self, amount):               # a method: a function that belongs to the object
        if amount <= 0:
            raise ValueError("Deposit must be positive")
        self.balance += amount

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("Not enough money")
        self.balance -= amount

ama = BankAccount("Ama", 100)     # an object, also called an instance
ama.deposit(50)
print(ama.balance)                # 150

    A class is the blueprint. An object is one thing built from it. self means “this particular object”. Each account keeps its own balance.

    The ideas behind it

    • Encapsulation: the object protects its own data. Nobody sets the balance directly; they go through deposit, which enforces the rules.
    • Inheritance: a class can extend another. class SavingsAccount(BankAccount) gets everything above and can add interest.
    • Polymorphism: different classes can offer the same method name, so code can use them without caring which it has.
    • Composition: an object contains other objects. A Bank has a list of accounts. Prefer this to deep inheritance; it stays simpler.

    Not everything needs a class. A few plain functions are often clearer. Use a class when data and the rules about it belong together.

    Do this

    You will spend more time fixing code than writing it. Debugging is a method, and people who follow the method fix things faster than people who guess.

    The method

    1. Reproduce it. Find the exact steps that make the bug happen every time.
    2. Read the error. All of it, from the last line up. It names the type of problem and the line.
    3. Form one guess about the cause, and decide what you would see if the guess were right.
    4. Check the guess by looking at real values, not by staring at the code.
    5. Fix the cause, not the symptom, then confirm the original steps now work.

    Looking at real values

    def average(numbers):
    print("DEBUG numbers =", numbers)      # the quickest tool there is
    return sum(numbers) / len(numbers)

    Better, use the debugger. In VS Code, click left of a line number to set a red breakpoint, then press F5. The program pauses there and you can inspect every variable and step forward one line at a time.

    When you are stuck

    • Halve the problem. Is the data correct at the midpoint? Then the bug is in the second half. Repeat.
    • Explain it aloud, line by line, to a person or an object on your desk. The act of explaining exposes the wrong assumption surprisingly often.
    • Search the exact error message in quotes.
    • Ask well: what you expected, what happened, the smallest code that shows it, and what you already tried.
    • Take a break. Many bugs are solved on the walk back.

    The usual suspects: a misspelt name, off-by-one in a loop, text where a number was expected, changing a list while looping over it, and assuming a value that is actually empty.

    The habits

    • Names say what things are. days_until_due, not d. Functions are verbs: send_invoice.
    • Functions do one thing and are short enough to see whole. If you need “and” to describe it, split it.
    • Do not repeat yourself. The same logic in three places will be fixed in two. Put it in one function.
    • No magic numbers. MAX_LOGIN_ATTEMPTS = 5 explains itself; a bare 5 does not.
    • Comments explain why, not what. The code already says what.
    • Handle the unhappy path. Empty input, missing file, no network.
    • Keep it simple. The clever solution is harder to debug than to write. Do not build for needs you do not have yet.
    • Format consistently with an automatic formatter, such as Black or Ruff for Python and Prettier for JavaScript, and stop arguing about spaces.

    Refactoring

    Refactoring is improving the structure of code without changing what it does: renaming, splitting, removing duplication. Do it in small steps and run your tests after each. Leave every file a little cleaner than you found it.

    Do this

    Two programs can give the same answer while one takes a second and the other takes a year. Big O is how engineers talk about that difference.

    Big O describes how the work grows as the input grows. We do not count seconds, because machines differ. We count steps as a function of n, the size of the input.

    Try it: how the work grows

    Drag n, the number of items. Watch which kinds of algorithm stay cheap and which explode.

    NameWrittenExample
    ConstantO(1)Looking up a key in a dictionary
    LogarithmicO(log n)Binary search: halving the problem each step
    LinearO(n)One loop over the items
    LinearithmicO(n log n)Good sorting algorithms
    QuadraticO(n²)A loop inside a loop over the same items
    # O(n²): compares every pair
def has_duplicate_slow(items):
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            if items[i] == items[j]:
                return True
    return False

# O(n): one pass, remembering what we have seen
def has_duplicate_fast(items):
    seen = set()
    for item in items:
        if item in seen:
            return True
        seen.add(item)
    return False

    With a million items, the first does around 500 billion comparisons and the second a million. Choosing the right data structure changed the growth rate. The same reasoning applies to memory used, called space complexity.

    Do not optimise everything. Write the clear version first, measure, and speed up only what is proven slow. But learn to spot a loop inside a loop over large data.

    Do this

    An algorithm is a precise recipe for solving a problem. You will rarely write the famous ones yourself, but learning them teaches you how to think.

    Searching

    Linear search checks every item: O(n). If the data is sorted, binary search looks at the middle, throws away the half that cannot contain the target, and repeats: O(log n).

    Try it: binary search

    Find the target in a sorted list. Each step checks the middle of what is left and discards half.

    def binary_search(items, target):
    low, high = 0, len(items) - 1
    while low <= high:
        mid = (low + high) // 2
        if items[mid] == target:
            return mid
        if items[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1

    A million sorted items take at most 20 steps.

    Sorting

    Simple sorts such as bubble sort are O(n²). Good ones such as merge sort are O(n log n). In real code, call the built-in: sorted(items) or items.sort(key=...). Implement one by hand once to understand it.

    Recursion

    A function that calls itself on a smaller version of the problem, with a base case that stops it.

    def total_size(folder):
    size = 0
    for item in folder["children"]:
        if "children" in item:
            size += total_size(item)     # a folder inside a folder: same problem, smaller
        else:
            size += item["size"]
    return size

    Patterns worth recognising

    • Divide and conquer: split, solve the parts, combine.
    • Graph traversal: breadth-first search finds the shortest path in steps; depth-first explores as far as possible first.
    • Dynamic programming: store answers to sub-problems so you never compute one twice.
    • Greedy: take the best-looking option at each step; fast, sometimes wrong.

    On a team, many people change the same code at once. Branches and pull requests are how that works without chaos.

    Branches

    A branch is a separate line of work. The main branch holds the working product. You make a branch for each change, so unfinished work never breaks main.

    git switch -c add-login          # create a branch and move to it
# ... edit, then ...
git add .
git commit -m "Add login form"

    Pull requests

    On GitHub you open a pull request: a proposal to merge your branch into main. Teammates read the changes, comment, and approve. Automated tests run. Then it is merged. This review step catches bugs and spreads knowledge.

    git switch main
git pull                         # get everyone else's merged work
git switch -c next-feature

    Merge conflicts

    If two people change the same lines, Git cannot choose and marks the file:

    <<<<<<< HEAD
price = 50
=======
price = 55
>>>>>>> add-discount

    Edit the file to the correct final version, delete the marker lines, then git add and commit. Conflicts are routine. Small, frequent pull requests keep them rare.

    Good habits

    • One pull request does one thing and is small enough to review in fifteen minutes.
    • Commit messages say why: “Fix total when cart is empty”.
    • Never commit passwords or keys. Use a .gitignore file to exclude them.
    • git diff before you commit; read your own change first.
    • Undo safely with git revert, which adds a new commit that reverses an old one.

    Do this

    A test is code that checks your code. Tests are what let you change software next month without fear of silently breaking it.

    pip install pytest
    # cart.py
def cart_total(prices, discount=0):
    if not 0 <= discount <= 1:
        raise ValueError("discount must be between 0 and 1")
    return sum(prices) * (1 - discount)

# test_cart.py
import pytest
from cart import cart_total

def test_adds_prices():
    assert cart_total([10, 20]) == 30

def test_empty_cart_is_zero():
    assert cart_total([]) == 0

def test_applies_discount():
    assert cart_total([100], discount=0.25) == 75

def test_rejects_bad_discount():
    with pytest.raises(ValueError):
        cart_total([100], discount=2)

    Run pytest in the terminal. Green means every check passed.

    Kinds of test

    • Unit tests check one function alone. Fast, and you write many.
    • Integration tests check parts working together, such as your code with a real database.
    • End-to-end tests drive the whole application like a user. Slow, so keep a few for the paths that matter most.

    What to test

    The normal case, the edges (empty, zero, one item, very large), and the invalid input. When you fix a bug, first write a test that fails because of it, then fix it. That bug can never return unnoticed.

    Test-driven development

    Write a failing test, write just enough code to pass, tidy up, repeat. It is not required, but it produces code that is easy to test, which tends to be well-designed code.

    Code that is hard to test is usually doing too much. Separate the logic from input, output and network calls, and the logic becomes simple to test.

    Do this

    Nearly all software talks over a network. Know what happens between pressing Enter and seeing a page, and half of web development stops being magic.

    What happens when you visit a page

    1. You type example.com. Your computer asks DNS, the internet’s phone book, for the numeric IP address of that name.
    2. Your browser, the client, opens a connection to that address, a server: a computer whose job is answering requests.
    3. The browser sends an HTTP request: “GET me the page at /”.
    4. The server sends an HTTP response: a status code and the content.
    5. The browser reads the HTML, requests the CSS, JavaScript and images it mentions, and draws the page.

    HTTP

    A request has a method, a path, headers (extra information) and sometimes a body (data being sent).

    MethodMeaningStatus codeMeaning
    GETRead something200OK
    POSTCreate something201Created
    PUT / PATCHUpdate something400Your request was invalid
    DELETERemove something401 / 403Not logged in / not allowed
    404Not found
    500The server broke

    Codes starting with 2 mean success, 4 means the client made a mistake, 5 means the server did.

    Other terms

    • HTTPS: HTTP encrypted, so nobody between you and the server can read or change it.
    • URL: the full address: protocol, domain, path and optional query, as in https://shop.com/items?page=2.
    • Port: a numbered door on a computer. Web servers use 80 and 443; while developing you will see localhost:8000, meaning “this computer, door 8000”.
    • JSON: the text format programs use to exchange data. It looks like Python dictionaries and lists.
    • API: a set of URLs a server offers for programs, not people, to call.

    The CSS ideas that matter

    Do this

    A modern front end is a program running in the browser. The challenge is keeping what is on screen in step with the data.

    State

    State is the data the screen depends on: the items in the cart, whether a menu is open, what the user typed. The clean approach: keep state in one place, and write a function that draws the screen from it. When state changes, redraw. Never let the screen and the data disagree.

    Components and frameworks

    Frameworks such as React, Vue and Svelte are built on that idea. You split the interface into components, reusable pieces that each take inputs and manage their own state, and the framework updates the page when state changes.

    The tools around it

    • Node.js runs JavaScript outside the browser. npm installs packages.
    • A build tool such as Vite bundles your files and reloads the page as you edit.

    What makes a front end good

    It loads fast, works on a phone, works from the keyboard and with a screen reader, shows a clear state while loading and when something fails, and never loses what the user typed.

    Do this

    The back end is the program on the server. It receives requests, applies the rules, talks to the database, and sends back data.

    REST: the common style

    URLs name things (/tasks, /tasks/7), and HTTP methods say what to do with them. Data travels as JSON. Status codes report the outcome.

    What a good API does

    • Validates every input. Never trust what a client sends. Here TaskIn rejects a request with a missing title.
    • Returns clear errors with the right status code.
    • Stays consistent in naming and shape.
    • Limits and paginates large lists.
    • Keeps secrets such as passwords and keys in environment variables, never in the code.
    • Is documented.

    Other back-end choices follow the same pattern: Django and Flask in Python, Express in JavaScript, Spring in Java, ASP.NET in C#, and Go’s standard library.

    Do this

    Authentication answers “who are you?”. Authorisation answers “what are you allowed to do?”. Getting either wrong is how data leaks happen.

    Storing passwords

    Never store a password. Store a hash: the output of a one-way function, with a random salt mixed in so identical passwords produce different hashes. At login, hash what was typed and compare. Use a function designed for passwords, such as bcrypt or argon2, through a library. If your database is stolen, the attacker gets hashes, not passwords.

    from argon2 import PasswordHasher     # pip install argon2-cffi
ph = PasswordHasher()

stored = ph.hash("correct horse battery staple")   # save this string
ph.verify(stored, "correct horse battery staple")  # True, or raises an error

    Staying logged in

    HTTP has no memory; each request arrives as a stranger. Two common solutions:

    • Sessions: after login the server creates a random session id, remembers which user it belongs to, and sends it to the browser in a cookie. The browser returns the cookie with every request.
    • Tokens: the server issues a signed token, often a JWT, stating who the user is and when it expires. The client sends it in a header. The server checks the signature instead of looking anything up.

    Authorisation

    Check permissions on the server for every request. Hiding a button in the front end protects nothing, because anyone can call your API directly. The classic bug: GET /orders/123 returns the order without checking that order 123 belongs to the person asking.

    Do not build it all yourself

    “Sign in with Google” uses a standard called OAuth. Hosted identity services and well-tested libraries handle login, password reset and two-factor codes. Use them. Your job is to understand what they do and to get authorisation right.

    Variables vanish when a program stops. A database keeps data safe, lets many users work at once, and answers questions about millions of rows in milliseconds.

    A relational database stores data in tables: rows are records, columns are fields. SQL is the language for asking it things. Popular ones are PostgreSQL, MySQL, SQL Server, and SQLite, which is a single file and already included with Python.

    The ideas

    • Primary key: a column that uniquely identifies each row.
    • Foreign key: a column pointing at a row in another table. This is the “relation”.
    • JOIN: combines rows from two tables that match.
    • Index: like the index of a book. It makes lookups on a column fast, at a small cost when writing. Missing indexes are the commonest cause of slow applications.
    • Transaction: a group of changes that all succeed or all fail. Moving money takes two updates; a transaction guarantees you never get only one.

    From code, safely

    import sqlite3
db = sqlite3.connect("shop.db")
city = input("City: ")
rows = db.execute("SELECT name FROM customers WHERE city = ?", (city,)).fetchall()

    Always pass values separately with ? placeholders. Building the query by gluing user text into the string allows SQL injection, where a user types SQL that your database then runs.

    Do this

    Code is easy to change. Data is not. A good table design makes every later feature simpler; a bad one is paid for daily.

    Start from the things and their relationships

    • One to many: a customer has many orders. Put customer_id on the orders table.
    • Many to many: a student takes many courses and a course has many students. Add a third table, enrolments, with student_id and course_id.
    • One to one: a user has one profile. Often the same table.

    Normalisation: store each fact once

    If a customer’s city is copied onto every order, a move means updating a hundred rows, and missing one leaves the data contradicting itself. Keep the city only on the customer and join when you need it. Break this rule deliberately, for speed, and only with evidence.

    Let the database enforce the rules

    Use NOT NULL, UNIQUE, foreign keys and sensible types. Application code has bugs; constraints hold regardless. Store money as whole numbers of the smallest unit or a decimal type, never as floating point. Store times in UTC.

    Migrations

    You will change the design after launch. A migration is a small versioned script that alters the database, such as adding a column. Migrations are kept in Git and run in order, so every copy of the database reaches the same shape.

    ORMs

    An object-relational mapper, such as SQLAlchemy, Django’s ORM or Prisma, lets you work with rows as objects in your language. Convenient, but learn SQL first so you can see what it does. The famous trap is the N+1 problem: one query for a list, then one more query for each item in it.

    Do this

    Architecture is how you divide a program into parts and decide who may talk to whom. Good structure makes change cheap.

    The two measures

    • High cohesion: things that change together live together.
    • Low coupling: parts know as little as possible about each other, so changing one does not break others.

    Layers

    A reliable default for most applications:

    1. Interface layer: receives HTTP requests, checks input, returns responses. No business rules.
    2. Business logic: the rules, such as “an order over the credit limit needs approval”. Knows nothing of HTTP or SQL.
    3. Data access: reads and writes the database.

    Because the rules sit alone in the middle, you can test them without a server or a database, and you can change the database without rewriting the rules.

    Principles that last

    • Single responsibility: each module has one reason to change.
    • Depend on interfaces: code against “something that can send a message”, not against one email provider. Swapping providers then touches one file.
    • Dependency injection: pass a component what it needs instead of letting it create it. This is what makes testing with fakes possible.
    • Simplicity first: build what is needed now, in a way that is easy to change later.

    Design patterns

    Named solutions to recurring problems. Know a few so you recognise them: Strategy (swap one algorithm for another), Observer (notify subscribers when something happens), Adapter (wrap something so it fits the shape you need), Factory (one place that decides which object to create), Repository (hide database access behind simple methods).

    Monolith or microservices

    A monolith is one application deployed as one unit. Microservices split it into many small services talking over the network. Microservices let large organisations work independently, at a heavy cost in complexity. Start with a well-organised monolith. Most products never need more.

    Write decisions down

    For any significant choice, write a short note: the context, the options, what you chose and why. Future engineers will thank you.

    Do this

    Servers handle thousands of users at the same moment. Concurrency makes software fast, and it creates a class of bug that appears only sometimes.

    The vocabulary

    • Process: a running program with its own memory.
    • Thread: a line of execution inside a process. Threads share memory.
    • Concurrency: making progress on several tasks by switching between them. Parallelism: truly running several at the same instant on different processor cores.
    • Async: one thread that starts a slow operation, such as a network call, and does other work while waiting.

    Most web work is waiting on the network or database, so async or threads help a lot. Heavy calculation needs multiple processes or cores.

    Race conditions

    balance = 100

def withdraw(amount):
    global balance
    if balance >= amount:         # A checks: 100 >= 80, fine
        # ... B runs here and also sees 100 ...
        balance = balance - amount

# Two withdrawals of 80 at once can both pass the check.
# The account ends at -60.

    A race condition is when the result depends on timing. It will pass every test on your laptop and fail in production under load.

    Defences

    • Do not share changing data. The simplest fix.
    • Locks: only one thread may be inside a critical section at a time. Beware deadlock, where two threads each hold a lock the other needs.
    • Let the database do it: transactions, and atomic updates such as UPDATE accounts SET balance = balance - 80 WHERE id = 1 AND balance >= 80.
    • Queues: put work on a queue and let workers take one job each.
    • Idempotency: design operations so that doing them twice has the same effect as once. Networks retry, so a “pay” request may arrive twice; an idempotency key lets the server ignore the repeat.

    Do this

    What changes when you go from a hundred users to ten million? A handful of building blocks, combined with judgement about trade-offs.

    Start simple

    One server and one database handle far more than beginners expect. Add complexity only when measurements say you must.

    The building blocks

    • Vertical scaling: a bigger machine. Simple, with a ceiling.
    • Horizontal scaling: more machines behind a load balancer that spreads requests. This requires stateless servers: no user data kept in a server’s memory, so any server can answer any request.
    • Caching: keep the result of expensive work somewhere fast, such as Redis, and reuse it. The hard part is knowing when the cached copy is out of date.
    • CDN: copies of your images, scripts and pages on servers near users worldwide.
    • Database replicas: copies that serve reads, while one primary takes writes.
    • Sharding: splitting data across several databases. Powerful and painful; a last resort.
    • Message queues: the web server puts slow work, such as sending email or resizing video, on a queue and replies immediately; workers process it later.
    • Rate limiting: capping requests per user to protect the system.

    The trade-offs

    • Consistency or availability: when machines cannot reach each other, you either refuse some requests or risk serving stale data. Banks choose consistency; a social feed chooses availability.
    • Latency or throughput, cost or speed, simplicity or flexibility. There is no best design, only a best fit for the requirements.

    How to approach a design question

    1. Clarify requirements: what must it do, for how many users, how fast, how reliable?
    2. Estimate the numbers: requests per second, data stored per year.
    3. Sketch the simplest design that works: client, server, database.
    4. Find the bottleneck and address it with one of the blocks above.
    5. State the trade-offs and the failure cases: what happens when each part dies?

    Do this

    Every application on the internet is probed by automated attacks within minutes of going live. Security is a habit in everyday code, not a final step.

    The rule under all the others

    Never trust input. Anything from a user, a browser, a file or another system may be hostile. Validate it on the server.

    The attacks you must know

    AttackWhat happensDefence
    SQL injectionUser text is run as part of a database queryParameterised queries, always
    Cross-site scripting (XSS)An attacker’s script runs in other users’ browsersEscape anything you put into a page; frameworks do this by default
    Cross-site request forgery (CSRF)Another site makes the user’s browser send a request to yoursCSRF tokens; SameSite cookies

    Principles

    • Least privilege: every user, service and key gets only the access it needs.
    • Defence in depth: several layers, so one failure is not a breach.
    • HTTPS everywhere.
    • Do not invent cryptography. Use well-known libraries.
    • Collect less data. What you do not store cannot leak. Know the privacy law that covers your users.
    • Log security events, and never log passwords or card numbers.
    • Fail closed: when a check errors, deny.

    Do this

    Software that runs only on your laptop helps nobody. Deployment is putting it on a computer that is always on and reachable.

    Linux

    Most servers run Linux and have no screen; you control them through the terminal, usually over SSH, a secure remote connection. The commands you learned at the start are the same ones. Add a few: cat and less to read files, grep to search, tail -f to watch a log, ps and top to see what is running.

    Configuration and environments

    The same code runs in several environments: development on your machine, staging for testing, production for real users. What differs, such as the database address and keys, comes from environment variables, never from the code.

    Containers

    “It works on my machine” is the oldest problem in software. A container packages your application with everything it needs, so it runs identically everywhere. Docker is the standard tool.

    The cloud

    Cloud providers rent computers and services by the hour. Three levels:

    • Platform services (Render, Railway, Fly.io, Vercel): hand over your code or container and they run it. Start here.
    • Virtual machines: a rented Linux server you manage yourself.
    • Managed services: a database, storage or queue run for you. Use a managed database; running your own safely is a job in itself.

    The large providers are AWS, Google Cloud and Azure. Their core ideas are the same: compute, storage, databases, networking, and permissions. Set a spending alert on day one.

    Do this

    Teams that release small changes many times a day have fewer outages than teams that release rarely. Automation is what makes that possible.

    Continuous integration

    Every time someone pushes code, a server automatically installs the project, runs the formatter check, the linter and all the tests. A red result blocks the merge. Problems are found in minutes, by a machine, before they reach users.

    Continuous delivery

    After the checks pass on the main branch, the same pipeline builds the container and deploys it, first to staging, then to production. Nobody copies files by hand.

    Making releases boring

    • Small changes. A ten-line release that breaks is found in a minute. A ten-thousand-line release is a week of detective work.
    • Feature flags: ship code switched off, then turn it on for a few users, then everyone. Deploying and releasing become separate decisions.
    • Gradual rollout: send 5% of traffic to the new version and watch the error rate before continuing.
    • Rollback: one command returns to the previous version. Practise it before you need it.
    • Database changes in two steps: add the new column first, deploy code that uses it, remove the old column later. Old and new code must both work during the switch.
    • Versioning: number releases, commonly as major.minor.patch, and keep a changelog.

    Infrastructure as code

    Servers, databases and networks are described in files, kept in Git and applied by a tool such as Terraform. The setup is reviewable, repeatable and recoverable.

    Do this

    Once real people depend on your software, you need to know it is healthy without waiting for them to complain.

    Three kinds of signal

    • Logs: timestamped records of what happened. Write them as structured data, include a request id so one request can be followed across services, and choose levels well: debug, info, warning, error.
    • Metrics: numbers over time. The four to watch for any service: request rate, error rate, response time, and how full its resources are.
    • Traces: the journey of one request through every service, showing where the time went.

    Look at the slowest responses, not the average. If one request in twenty takes eight seconds, the average hides it and your users do not.

    Alerts

    Alert on what users feel, such as errors and slowness, and make every alert something a person must act on. Alerts that cry wolf get ignored, and then the real one is missed.

    When it breaks

    1. Stop the harm first. Roll back or switch the feature off. Understand it afterwards.
    2. Communicate: tell the team and the users what is known, at regular intervals.
    3. Write a blameless review: what happened, why the system allowed it, and what will change. The question is never “who”, always “how did our process let this through”.

    Performance

    Measure before you optimise. A profiler shows where time is actually spent, and it is rarely where you guessed. The usual culprits, in order: too many database queries, a missing index, doing work on every request that could be cached, sending too much data, and only then slow code.

    Reliability targets

    Decide how reliable the service needs to be, such as 99.9% of requests succeeding, and measure against it. Perfection is not the goal; it costs too much and slows everything down. Also test your backups and have a written plan for losing a server or a database.

    Do this

    Software is built by groups. The engineers who grow fastest are the ones who communicate clearly and make the people around them more effective.

    From idea to release

    Work usually arrives as a ticket describing a problem. Before writing code, make sure you understand who it is for and how you will know it is done. Many teams work in short cycles, often called sprints, with a brief daily check-in and a board showing what is to do, in progress and done. The labels vary; the point is small steps and frequent feedback.

    Requirements

    The most expensive bugs are building the wrong thing. Ask questions early. Repeat the request back in your own words. Agree on examples: “when the cart is empty, the button is disabled”.

    Code review

    As the author: keep the change small, explain what and why in the description, review your own diff first, and receive comments as help with the code, not judgement of you.

    As the reviewer: look for correctness, clarity, tests and security. Be specific and kind. Ask questions (“what happens if this list is empty?”). Say what is good too. Do not block on personal taste.

    Estimating

    Estimates are guesses. Break the work into pieces of a day or less, give a range, and say immediately when the range turns out wrong. Bad news early is a professional skill.

    Writing

    Engineers write constantly: a README that gets a newcomer running in ten minutes, a design document that states the problem and the options before the choice, a bug report with steps, expected and actual results. Clear writing is clear thinking made visible.

    Technical debt

    Shortcuts taken to ship faster are a loan. Some debt is sensible. Unpaid, the interest is every later change taking longer. Record it and pay it down steadily.

    Being good to work with

    Ask for help after a fair attempt, and show what you tried. Say “I do not know” without embarrassment. Share credit. Take responsibility when you break something. Help the next person learn what you just learned.

    Do this

    AI assistants now write a large share of code. They make a capable engineer much faster and a careless one dangerous. The difference is whether you understand what you ship.

    What they are good at

    Explaining unfamiliar code and error messages, drafting routine code and tests, translating between languages, suggesting approaches, and reviewing your work for mistakes.

    Where they fail

    They produce confident code that is subtly wrong, call functions that do not exist, miss requirements you did not state, introduce security holes, and do not know your codebase unless shown it. They do not carry responsibility. You do.

    Rules for using them well

    • Never merge code you cannot explain line by line.
    • Give context: what the code is for, the constraints, the surrounding code, and an example of the result you want.
    • Ask for a plan first on anything large, then build in small steps you can check.
    • Test everything it writes. Your tests are how you verify a machine’s work.
    • Review for security especially: input validation, access checks, secrets.
    • Do not paste secrets or private data into tools your employer has not approved.

    While you are learning

    If the assistant writes your exercises, you learn nothing, and the fundamentals are exactly what let you judge its output later. Write the code yourself first. Then ask the assistant to review it, explain an error, or show another approach. Use it as a tutor.

    The engineers who do well alongside these tools are the ones who can specify a problem precisely, read code critically, design systems, and take responsibility for results. Those are the skills this course trains.

    Getting the first job

    • Portfolio: two or three deployed projects with clean code, tests and good READMEs beat twenty tutorials.
    • CV: one page; lead with what you built and what it achieved.

    Levels

    How to use extra material without drowning

    Finish a part of this course, then pick one resource for that stage and do its exercises. One finished course and several built projects beat ten bookmarked ones.

    The jargon in this course, one sentence each.

    Algorithm
    A precise step-by-step recipe for solving a problem.
    API
    A set of URLs or functions one program offers for other programs to call.
    Authentication
    Proving who a user is.
    Authorisation
    Deciding what a known user is allowed to do.
    Back end
    The code that runs on a server: rules, data access and APIs.
    Big O
    A way of describing how an algorithm’s work grows as its input grows.
    Branch
    A separate line of work in Git.
    Bug
    A mistake that makes software behave wrongly.
    Cache
    A fast store of results kept so that expensive work is not repeated.
    CI/CD
    Automation that tests every change and deploys it.
    Class
    A blueprint for objects, bundling data with the functions that work on it.
    Client
    The program that makes a request, such as a browser or app.
    Commit
    A saved snapshot of a project in Git.
    Compiler
    A program that translates source code into machine code ahead of time.
    Container
    A package of an application with everything it needs to run the same anywhere.
    Database
    Software that stores data safely and answers questions about it.
    Deploy
    To put software onto servers where users can reach it.
    DNS
    The system that turns a domain name into a numeric address.
    DOM
    The browser’s tree of objects representing a page.
    Environment variable
    A setting supplied to a program from outside its code.
    Framework
    A library that provides the structure of an application for you to fill in.
    Front end
    The part of an application the user sees and touches.
    Function
    A named, reusable piece of code that takes inputs and returns a result.
    Git
    The standard tool for tracking changes to code.
    Hash
    The output of a one-way function, used for fast lookup and for storing passwords.
    HTTP
    The request and response protocol of the web.
    Index
    A database structure that makes lookups on a column fast.
    JSON
    A text format for exchanging structured data.
    Library
    Code written by others that you install and call.
    Load balancer
    A component that spreads requests across several servers.
    Migration
    A versioned script that changes a database’s structure.
    Object
    One thing created from a class, with its own data.
    Pull request
    A proposal to merge a branch, reviewed by teammates first.
    Race condition
    A bug where the result depends on the timing of simultaneous operations.
    Recursion
    A function solving a problem by calling itself on a smaller version of it.
    Refactoring
    Improving the structure of code without changing what it does.
    Repository
    A project’s folder together with its Git history.
    REST
    A common API style: URLs name things, HTTP methods act on them.
    Server
    A computer or program that answers requests.
    SQL
    The language for querying relational databases.
    State
    The data a program is currently holding that its behaviour depends on.
    Technical debt
    The future cost of shortcuts taken today.
    Test
    Code that checks other code behaves as intended.
    Transaction
    A group of database changes that all succeed or all fail together.
    Variable
    A name that holds a value.
